# Downloadable correction models — T-08 foundation

Baseline: PristinePage v0.3.4, `5c184dc`. This increment implements the private storage portion of [T-08](../../docs/specs/IMPLEMENTATION_PLAN.md#task-t-08--provider-registry-and-optional-source-adapters). It does not change the accepted implementation plan, provide model inference, activate a carousel card, or authorize an asset or runtime acquisition.

## Runtime choice

Prefer [ONNX Runtime Android](https://onnxruntime.ai/docs/tutorials/mobile/) with the standard Android package on CPU for the first qualification. It runs compatible already-exported ONNX files and has Java and C/C++ integration. [ORT-format optimization documentation](https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-model-runtime-optimization.html) distinguishes full and minimal builds. Support for the artifact's format does not establish its operators, opset, API26/arm64 footprint, execution time, numerical parity, license or ability to fit an Android device. Start with one runtime and measure; an operator-reduced build can shrink deployment later at the cost of narrowing custom model compatibility.

Maven Central metadata on 2026-11-21 lists `1.32.0`; a headers-only probe of the [Android AAR](https://repo.maven.apache.org/maven2/com/microsoft/onnxruntime/onnxruntime-android/1.32.0/onnxruntime-android-1.32.0.aar) reports 59,335,382 bytes. That is the complete distribution archive, not the installed arm64 increment, model download size or inference RAM. The adjacent SHA-256 URL returned 404. Verify exact binary provenance, compute a local digest, audit contents/notices and measure the packaged arm64 delta before adopting a runtime.

- [DocQuad in MakeACopy](https://raw.githubusercontent.com/egdels/makeacopy/1041932d2c9906d3e907a1bbae59022e845a7e25/README.md) is precedent for Android document detection with ONNX Runtime CPU; the [pinned asset listing](https://api.github.com/repos/egdels/makeacopy/contents/app/src/main/assets/docquad?ref=1041932d2c9906d3e907a1bbae59022e845a7e25) reports a 13,404,960-byte ORT export and the maintainer declares Apache-2.0 for the model. The Git blob ID is not the file's SHA-256. Its [Android build](https://raw.githubusercontent.com/egdels/makeacopy/1041932d2c9906d3e907a1bbae59022e845a7e25/app/build.gradle) targets min API 29, not PristinePage's API 26. This is an install/inference witness candidate, not a learned dewarper or proof of compatibility with the retained API 28 emulator.
- [Paddle UVDoc ONNX](https://huggingface.co/PaddlePaddle/UVDoc_onnx/blob/3bcf535371727d11e783101f79a504c68848aae3/README.md) is the first candidate for actual learned document unwarping. The exact tree lists a 31,684,150-byte `inference.onnx` and an Apache-2.0 model-card declaration. Its current documented desktop path does not prove this binary's Android behavior. It must not pass as the original map-returning UVDoc or get an invented paired mask transform.
- For document appearance, the [FSENet ONNX port](https://github.com/fabio-sim/DocShadow-ONNX-TensorRT/releases/tag/v1.0.0) lists approximately 114.5 MiB per graph; weight terms, exact graph equivalence and handset fit remain unresolved. GCDRNet is a relevant appearance research candidate but its published source does not provide a verified ready-to-run graph and weight license. Prefer a genuinely compact, pre-exported document shadow or illumination candidate before enabling a card. A global low-light enhancer is not automatically a document deshadower.
- For optional photo work, [Real-ESRGAN's small general model](https://aihub.qualcomm.com/models/real_esrgan_general_x4v3) has small published model-size metadata and a [separate ncnn implementation](https://github.com/xinntao/Real-ESRGAN-ncnn-vulkan). That is super-resolution, not scratch repair. [DDColor-Tiny](https://github.com/piddnad/DDColor) has an upstream checkpoint, and [DeOldify-ONNX](https://github.com/instant-high/deoldify-onnx) is a third-party colorization lead, not historically verified color. [Bringing Old Photos Back to Life](https://github.com/microsoft/Bringing-Old-Photos-Back-to-Life) demonstrates scratch-specific processing, but its upstream implementation uses Python/checkpoints rather than demonstrating a ready Android artifact. None of these are selected; exact compatible graph, weight terms, performance and acceptable output still need review.

[LiteRT](https://ai.google.dev/edge/litert/android/quickstart) is the next general-purpose option when a relevant `.tflite` graph is already available. [ncnn](https://github.com/Tencent/ncnn) is an Android-capable native CPU/Vulkan candidate for models distributed in its format, not a direct replacement for an ONNX catalog. [MNN](https://github.com/alibaba/MNN) has on-device inference and a [Sana Android example](https://github.com/alibaba/MNN/tree/master/apps/sana); its [converter documentation](https://github.com/alibaba/MNN/blob/master/docs/tools/convert.md) describes converting ONNX and other inputs into MNN models. [ExecuTorch](https://docs.pytorch.org/executorch/stable/using-executorch-android.html) has an Android AAR; choose it only for a compatible exported program already available. [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp) has supported image-editing/generation families and an Android precedent, but it is not a general restoration tensor runtime. No model or runtime bytes were downloaded for this assessment.

## First storage contract

The application will own one store for a dedicated private model directory, independent from sources, rendered pages, exports and share files. This package-internal implementation is synchronous and must be called on a worker dispatcher by that owner, not bound to Compose or Room transactions. The store accepts a caller-supplied stream and an exact versioned identity, with a positive byte extent capped at 512 MiB per asset, SHA-256 and separately optional peak inference RAM metadata. It checks closed bytes before publishing with a same-directory atomic move. It verifies bytes again before issuing an exact-file lease and refuses removal while any lease for that identity remains active. A valid weight file is `VERIFIED` only as bytes, not admitted as a correction. Startup staging cleanup is for the store's own interrupted-install files only, before other users of that directory; never scan a shared path or follow links. These are process-level guarantees for one app-private writer; they are not power-loss or cross-process coordination claims.

Private filenames deliberately do not identify a graph format. For DocQuad's trusted ORT profile, the adapter must pass `session.load_model_format=ORT` per the [runtime documentation](https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-models.html) rather than relying on an `.ort` suffix. Custom model import cannot assign a profile based on a filename.

## Integration gates

- Smallest real-runtime qualification proposal: obtain only the exact Maven Android package above and the pinned DocQuad inference asset (about 69.4 MiB combined by advertised lengths, excluding any separately reviewed dependencies or notices). Verify provenance, rights, SDK/ABI compatibility and included native size; use CPU first on synthetic marked pages. Only then add the exact pinned Paddle UVDoc graph (another 30.2 MiB) and prove independent geometry and image-output semantics. This is a proposed acquisition scope, not an approval or an installed dependency.
- The Correction carousel should retain the current bundled example pattern. A downloadable card has a top-right arrow-to-bar, a non-gesture accessibility action, and explicit confirmation stating download and installed storage plus any larger staging allowance. RAM is a separate field; use an attributable bound/measurement with its workload or “Not yet measured.” Installation keeps the model until explicitly removed. Long-press and an accessible details action expose a second, explicit removal confirmation. A final **Add custom model** entry accepts only a supported, bounded model/profile contract, not arbitrary code, directories or a filename-derived tensor interpretation. Learned geometry attaches to the crop/frame flow rather than bypassing it as an image look.
- Transport remains separate: use browser download and the [Android document picker](https://developer.android.com/training/data-storage/shared/documents-files) to preserve the current no-Internet manifest, or explicitly approve in-app catalog-only HTTPS. Android's [DownloadManager](https://developer.android.com/reference/android/app/DownloadManager) also requires Internet permission. Neither path may send photos, albums, private paths or recipe contents. Loading or rendering never starts retrieval.
- Before learning-based recipes can be saved, persist and independently pin a verified rendition with its recipe/revision and provenance. Exported files and pinned accepted renditions must remain unchanged when weights are deleted. Reprocessing or exporting at a new size may require reinstalling the exact model; do not substitute another model or conflate a saved preview with full-resolution output. In-flight runs and immutable snapshots retain their existing ownership guarantees. Confirm with a real learned save → delete → reopen/export test before claiming it works.
- Asset identity/terms, typed profile/adapter, graph compatibility, CPU parity, measured memory and fidelity, native UI, and direct-download approval are separate. No gate is retired based on the storage design or synthetic bytes.

## Independent review

The initial review found two Important defects: an external stream callback held the store lock used by unrelated leases, and cancellation was not checked after a transfer began. The concurrent release regression reproduced a timeout while the source was deliberately paused; the cancellation regression showed that canceling at the stream's close did not prevent publication. The correction reserves and publishes under the store lock but streams and verifies outside it, releases each lease once without a second monitor, and calls the caller's nonblocking cancellation checkpoint through copy, readback and immediately before the atomic commit. Cancellation after a committed move does not uninstall the asset. The review's Minor gap remains: host coverage does not yet exercise symlink refusals. No Android or power-loss result is implied.

Nine focused JVM cases passed after both review corrections, including the same concurrent-release and cancellation regressions. The final strict-offline Gradle run passed the five JVM suites (1,463 cases total, 234 in `image-android`) and app lint (0 errors, 21 warnings). Removal is exercised on a real temporary filesystem with separate saved bytes; this is not end-to-end learned-recipe retention.

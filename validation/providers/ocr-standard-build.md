# Standard offline OCR build

Both standard app variants use the same offline Tesseract runtime and 20 pinned recognition files. The app has no OCR-free flavor and does not fetch language packs at runtime. Keep these third-party files out of Git. Assembly is not authorization to distribute the resulting APK.

## Stage already approved inputs

Use Python 3.11 or later and an input directory containing exactly the named prerequisites below (other retained inputs are not copied). Keep them at their original byte lengths and digests. The stage command does not perform downloads or need a previous private validation receipt, font files, or test images.

- `tesseract4android.aar` from the [pinned standard JitPack coordinate](https://jitpack.io/cz/adaptech/tesseract4android/tesseract4android/4.9.0/tesseract4android-4.9.0.aar); use the exact SHA-256 in the [qualification record](ocr-tesseract-qualification.md).
- The 20 `<code>.traineddata` files named in the [pin table](tessdata-fast-4.1.0-pins.tsv), from the [pinned tessdata_fast tree](https://github.com/tesseract-ocr/tessdata_fast/tree/65727574dfcd264acbb0c3e07860e4e9e9b22185).
- `wrapper-license.txt` from the [Tesseract4Android tag](https://github.com/adaptech-cz/Tesseract4Android/blob/4.9.0/LICENSE); `tessdata-license.txt` from the [recognition data tree](https://github.com/tesseract-ocr/tessdata_fast/blob/65727574dfcd264acbb0c3e07860e4e9e9b22185/LICENSE).
- Unmodified vendored legal texts from the [wrapper tag tree](https://api.github.com/repos/adaptech-cz/Tesseract4Android/git/trees/15c534717b1cb58261b58d4e4c1200c7f81f668c?recursive=1), saved as `vendored-tesseract.bin` (Tesseract `LICENSE`), `vendored-leptonica.bin` (`leptonica-license.txt`), `vendored-jpeg.bin` (IJG `README`) and `vendored-png.bin` (libpng `LICENSE`). The `.bin` names preserve the original downloaded bytes; these are text notices.
- The exact [`clang-r522817c` NOTICE](https://android.googlesource.com/platform/prebuilts/clang/host/linux-x86/+/ndk-r27c/clang-r522817c/NOTICE), passed as a separate file. This software is based in part on the work of the Independent JPEG Group.

From the repository root, prepare the ignored build stage once. Use a fresh stage path, not a link. If it already exists, verify it without `--from-publisher`; do not repurpose it if verification fails.

```text
python -B validation/providers/prepare_ocr_local_app.py validation/raw/providers/ocr-app-standard --from-publisher <verified-inputs> --clang-notice <verified-clang-notice>
python -B validation/providers/prepare_ocr_local_app.py validation/raw/providers/ocr-app-standard
```

The preparer verifies each source file before staging, extracts compile classes from the exact AAR, and verifies the resulting exact inventory. The common Gradle pre-build task authenticates it again for both variants. Use the [normal pinned, strict-offline Gradle setup](../../README.md#current-build-baseline). For review, run the preparer with `--apk <path-to-apk>` to authenticate the packaged payload independently of Gradle; also check the manifest, DEX, alignment, signing identity (debug only), and the installed app/test hashes.

## Local qualification and release boundary

The first standard debug build (`0.5.0-debug`, Android code 8, app digest `f95444512cd90d48ac30902e44ef07180b6731e0331b9ab2ee4a313e8b861694`, test digest `dce6fba805a72292ec4ce5469b5ad4b8373511e5b44e826593a1825e45deb9c1`) passed a cold English system Files → Natural lightness → save → automatic OCR → exact Home reopen journey in airplane mode on a retained LDPlayer API 28 guest. The runner verified the installed bytes before execution, radio isolation and restoration, both original emulator process exits, and release. This was an update on a retained guest, not a first installation, fresh 20-language run, or product release qualification.

The SDK build and verification passed for the successor debug `18dde345a06f1d8c15a0ef771343bc4108eaeee2ed9f6ffe26f26cec1e7c56e4`, its test `54da7bb290de188bbda3b662ebc9d4685a3fea0c6ea7d26d687d7c4bbd8a54f0`, and unsigned release `0941588ca634c4cabfb0843d7b06ab5f49555c4f195b5063b1c2584ad9a2f20e`. The build recorded 1,640 JVM tests with no failures or skips, including the new failed-linkage check on a host with no Android native runtime; 43 provider host checks independently passed. Before marking OCR ready or enrolling new work, the runtime now initializes the native wrapper classes off the UI thread, then admits the exact packs. That is a load check, not a successful engine initialization or recognition claim. There was no dependency acquisition or version change: the release configuration was missing two existing EJML coordinates in the `data` and `image-android` lockfiles; the exact existing versions were added only to those two release configurations.

The retained ARM64 AAR members have no `DT_NEEDED` entry for `libc++_shared.so`; the exact Tesseract member nevertheless defines C++ exception-handling symbols, including `__cxa_throw` and `__cxa_allocate_dependent_exception`. The pinned Clang notice is evidence, not proof of complete static linkage or notice coverage. The [native diagnostic probe](ocr-tesseract-qualification.md#native-diagnostic-admission-remains-open) demonstrates a path-bearing descriptor-2 diagnostic on an induced missing-pack initialization, not an ordinary app disclosure. An exact reviewed linkage/notice inventory and a scoped native diagnostic fix and failure-path witness are still required before integration under the [publication gate](../../docs/specs/OPERATIONAL_PLAN.md#standard-ocr-build).

The [upstream Tesseract log sink](https://github.com/tesseract-ocr/tesseract/blob/5.5.1/src/ccutil/tprintf.cpp) defaults to `stderr` and can redirect its own `tprintf` stream. Supplying `debug_file` in the wrapper's [initialization map](https://github.com/adaptech-cz/Tesseract4Android/blob/4.9.0/tesseract4android/src/main/java/com/googlecode/tesseract/android/TessBaseAPI.java#L408) does not solve early pack-open failure: the engine [tries opening the pack before it applies the map](https://github.com/tesseract-ocr/tesseract/blob/5.5.1/src/ccmain/tessedit.cpp#L79-L135). A pre-init `SetVariable` is a candidate for that one Tesseract sink, not a substitute for [Leptonica's own handler](https://github.com/DanBloomberg/leptonica/blob/1.85.0/src/utils1.c#L310-L390) or direct Android log calls seen in the packaged libraries.

Next qualification decision: prefer upstream controls only if they cover all relevant sinks on the exact existing binary, including initialization failure. If they cannot, evaluate a source-built, scoped diagnostic patch of the same engine/version with the actual native build/link inputs and complete notices. Do not redirect app-wide stdout/stderr or Android logging, assume a tagged notice proves final linkage, or switch OCR engines to avoid this check. A new source/toolchain acquisition or newly built runtime must be separately authorized and requalified.

# Tesseract4Android and multilingual pack qualification

The operator approved private acquisition of the standard Tesseract4Android `4.9.0` AAR/POM, 20 named `tessdata_fast` `4.1.0` recognition files, and their publisher provenance and notices. The exact AAR is 12,848,454 bytes, SHA-256 `bce5d6413a1a5ae3d7240033fbbc851ba3217d0a08d9769400e17a077f42cb2a`. It was obtained from the [pinned JitPack coordinate](https://jitpack.io/cz/adaptech/tesseract4android/tesseract4android/4.9.0/tesseract4android-4.9.0.aar); the digest identifies the observed bytes, not an independently published signature. The POM lists only `androidx.annotation:annotation:1.3.0` at runtime. There is no Gradle repository or dependency change in this qualification.

All 20 files match the pinned [publisher tree](https://api.github.com/repos/tesseract-ocr/tessdata_fast/git/trees/65727574dfcd264acbb0c3e07860e4e9e9b22185?recursive=1) in both exact length and Git blob SHA-1. Their [SHA-256 values and lengths](tessdata-fast-4.1.0-pins.tsv) were calculated and independently rechecked on the retained files for future app identity checks. The packs sum to 50,008,092 bytes; the AAR plus those packs is 62,856,546 bytes. No extra layout/script model was acquired. The provider bytes and raw request evidence stay outside Git.

The AAR's own text manifest declares `minSdkVersion=21`, no permissions or components. It contains JPEG, Leptonica, PNG and Tesseract libraries for four ABIs. All four ARM64 ELF libraries have 16 KiB-aligned load segments with congruent file and virtual offsets. Their `DT_NEEDED` inventory points to the other packaged libraries or Android system libraries (`libc`, `libdl`, `libm`, `liblog`, `libjnigraphics`, `libz`), with no shared C++ runtime entry. This does not determine static runtime or notice obligations. The exact JVM class exposes `init`, `setPageSegMode`, `setImage(Bitmap)`, `getUTF8Text`, `stop` and `recycle`; this is static inspection, not JNI execution. Inspect the eventual app's merged manifest, APK ZIP alignment and native loading before Android use.

There are no notice files inside the AAR's ZIP. The [wrapper tag tree](https://api.github.com/repos/adaptech-cz/Tesseract4Android/git/trees/15c534717b1cb58261b58d4e4c1200c7f81f668c?recursive=1) contains the vendored Tesseract `LICENSE`, Leptonica `leptonica-license.txt`, IJG JPEG `README` and libpng `LICENSE`. Each exact file was retrieved and checked against that tree. Keep the wrapper and trained-data Apache-2.0 texts as separate source evidence. The pinned wrapper [README](https://github.com/adaptech-cz/Tesseract4Android/blob/4.9.0/README.md) describes Tesseract 5.5.1, Leptonica 1.85.0, IJG libjpeg v9f and libpng 1.6.48. Before redistribution, tie the actual native inventory to the corresponding build selections and required notices, including IJG attribution and any bundled native toolchain/runtime material. Matching vendored source licenses is not proof of AAR build reproducibility or final notice closure.

The [synthetic multilingual probe](probe_ocr_language_packs.py) returned nonempty recognition on all 20 single-language samples using the acquired packs with the already installed **desktop Tesseract 5.3.3**, and all 20 matched after NFC, case and whitespace normalization. English/French and Japanese/English mixed controls matched; Arabic/English returned text but did not exactly match (sequence similarity 0.9839). These high-contrast generated lines do not establish Android 5.5.1 recognition, real-page accuracy, mixed-script bidi fidelity, OCR-to-FTS search, latency or RAM. The nonexact RTL mixed result remains an acceptance case, not a waiver.

## Private Android probe

The isolated [instrumentation probe](android-ocr-probe/app/pristinepage/image/LocalTesseractProbeTest.java) is not in a normal source set. The initial S-01 development test package (`b5745027479f75107ca411cfe9e3e1723f6eb5c579ccb9025405567217f98276`) ran the exact standard AAR's four ARM64 libraries on owned LDPlayer API 28, with no Internet permission in its manifest. All 20 single-language controls returned text and 19 matched under single-block segmentation. Japanese missed one character in an 18-character control, making the initial exact-single-language test fail. The English/French and Japanese/English mixed controls were exact; Arabic/English had two edits in 63 normalized characters and retained both scripts. Blank produced empty normalized output. No page data or installed PristinePage app was used or altered.

The hardened diagnostic package (`8b6a9fe949622710f030c22025cdc51bfd0c0b6ff37deeee82090cdb4485984b`) tested the same hashed Japanese PNG: Single block (6) and Automatic (3) each returned one non-punctuation edit and missed the exact receipt keyword. Sparse text (11) was exact and retained the keyword. The Japanese capability control now explicitly uses Sparse text while the hold-pixels diagnostic retains all three observations. This does not change an app default, establish that Sparse text is generally preferable for Japanese pages, or clear exact-page search under Automatic. The mixed controls use separate lines; text in both scripts and verified available packs do not independently enumerate which native models were loaded.

The final development test APK `3e4b1b4aa210fd2a1d05e7c2ea77fbbedd877a390168223a50abe9e807a3b09c` matched its installed bytes with four byte-identical ARM64 libraries and all 20 exact packs. Both instrumentation methods passed: all 20 single-language controls were exact under their declared layouts, the two earlier exact mixed controls remained exact, Arabic/English remained two edits in 63, and blank returned an actual empty string. This is **23 of 24 exact controls**, not 24. The same Japanese layout discrepancy reproduced. Ten evidence hashes, both original emulator process exits and allocator release were verified; prior test artifacts and guest data were retained.

### Reproduce locally

Use the [preparer](prepare_ocr_android_probe.py) with the already approved private input directory, installed font directory, and a fresh `ocr-engine-…` run name. It authenticates the exact AAR, packs and known notices before staging any files. The reported `OCR_STAGE_RECEIPT_SHA256` is recorded independently of the generated tree. Invoke the [optional test init script](local-ocr-engine-test.init.gradle) with `--offline --dependency-verification=strict`, `-Dpristinepage.ocrProbe=<absolute-stage>`, `-Dpristinepage.ocrProbeReceipt=<recorded-sha256>`, and only `:image-android:assembleDebugAndroidTest`. A different receipt was refused before signing; the verified stage passed. Before guest mutation, inspect the SDK-verified artifact, verify the installed bytes and the exact ABI and language inventory, and apply the shared LDPlayer allocator and exact test-package rules. Do not package or publish these inputs in an ordinary app build.

The stage's included wrapper, trained-data, Tesseract, Leptonica, IJG JPEG and libpng notices do not close the linked Android NDK r27c (`12479018`) runtime's notice obligations. Java bounds the PNG header dimensions before bitmap allocation and caps the returned Java string before normalization, not native engine/JNI allocations. Metrics contain only synthetic case IDs, edit counts, layouts and elapsed times. Treat lower-level test and engine output as private. These measurements do not establish representative-document fidelity, production integration, process-death handling, physical-device resources, or redistribution clearance.

### Private saved-page probe

The [saved-page instrumentation](android-ocr-probe/app/pristinepage/image/LocalSavedOcrIntegrationTest.kt) uses the same receipt-gated Gradle task and exact stage as the direct JNI probe. It asserts that the test APK targets itself and has no Internet permission, redirects Room and source storage to a fresh synthetic root, and imports 24 exact PNG controls through the real ingest boundary. It renders each saved recipe from committed source pixels with the same budget used by ingest, then uses the exact ordered persisted pack configuration in the real Tesseract session. The real worker commits recognition and the FTS projection with the producing job. The shared Java utilities remain package-private and test-only.

The first assembly failed at test compilation on the fixture's wrong `ImportBatch` accessor. Independent source review identified one Important evidence gap: the original assertion could miss extra page hits and could not distinguish a successful empty result from failure after reopen. Two Minor gaps concerned independent pack-order checks and a direct isolation witness. The corrected test checks the complete ID sets and each hit's navigation guard, with explicit single/mixed overlap and an absent-text query. It checks the expected ordered selections and verifies that the isolated file materialized. After store close/reopen it requires durable terminal work for all 24 pages, then reads only a scalar from the synthetic database to prove the blank's exact producer is `SUCCEEDED` and its stored result is empty. These are coordinator corrections, not a second independent review.

The exact S-01 test APK `8a73b56ea810ff8d7861d5c21d6062aecb5466848787f11c8b77f343ff589248` passed its one named instrumentation method on LDPlayer API 28. The installed bytes matched; SDK inspection verified no Internet permission and all four ARM64 binaries, staged assets, and 20 packs matched their pins. All 20 single-language controls were exact under their declared layouts, with Sparse text for the single Japanese control. English/French and Japanese/English were exact, Arabic/English retained both script anchors with two edits in 63 normalized characters, and blank returned and retained an empty string: **23 of 24 exact**. All 24 search checks matched before close and again after reopen (**48 complete hit-set checks**). The shared image reservation returned to zero after every page; that is not a native heap or latency measure. Four focused stage-verifier host tests passed. Ten evidence hashes, both original emulator process exits and allocator release were verified. Prior artifacts and synthetic guest data were preserved.

This probe uses controlled PNGs and their initial saved recipes; it does not compare an edited raster against the original, drive the UI, test WorkManager or kill a process. The test package lacked Internet permission; no radio-setting mutation or whole-app airplane-mode test was performed. The direct probe's Japanese Automatic gap remains. The ordinary app still does not package or activate this runtime, and the native notice, representative-document, and production acceptance gates remain open.

### Important — LIBRARY-I1: navigation can admit a second preparation and overwrite the first durable request

**Evidence status: true by control flow; not executed as a new Kotlin/device regression here.** Locations: `app/src/main/kotlin/app/pristinepage/library/ImportLibrarySession.kt:40-43,65-74,118-126`; enabled navigation: `app/src/main/kotlin/app/pristinepage/library/LibraryScreen.kt:73-75`.

`prepare` uses the shared `loading` Boolean as its only in-flight preparation guard, captures destination A, and suspends in `actions.load`/`actions.begin`. Open remains enabled and its independently completing `loadSelected` sets loading=false. Therefore: begin A and suspend its preparation; open B and finish its metadata read; begin B, persist/offer B's request; then let A's preparation finish. Line 73 unconditionally replaces B with A, without checking an import-preparation token or the now-existing request. Both durable reservations can exist in different documents; an already launched B result is then ignored by line 79 and its registration can be removed. No page is reassigned to A, but B's user selection/request is abandoned from the active UI and a second picker can be offered unexpectedly. The first-run create-then-prepare path also calls parameterless `prepare()` after suspension, so it must not derive its intended created-document destination from intervening navigation.

**Fix:** give preparation its own Main-confined operation identity/admission flag, independent of navigation/loading. Permit navigation without admitting a second import preparation or replacing another active request. Retain the captured destination through the entire create/reserve sequence; reconcile any already persisted superseded reservation rather than silently dropping its ID. Add deferred-load/begin host regressions with A/B navigation and reverse completion order, plus a create/import navigation case; retain exact one-shot launch and bound-destination evidence. Disabling only the visible Import button is insufficient if Open can clear the shared guard.

### Important — LIBRARY-I2: an older overview read can undo the completion-refresh correction

**Evidence status: true by control flow; the new overlapping-read case was not executed here.** Locations: `app/src/main/kotlin/app/pristinepage/library/ImportLibrarySession.kt:54,90-94,111-127`.

The listing token guards only the library-list assignment. `loadSelected` guards only navigation/selected ID, not the metadata generation or the refresh that owns loading. During COPYING, Refresh is enabled. Its selected-document read can obtain an old snapshot and suspend delivery. The copy then commits, publishes COMPLETE/loading=true, and its own reload/load publishes the new pages. Deliver the older read afterward: navigation and selected ID still match, so lines 125-126 overwrite the new overview and clear loading. The UI can again show settled COMPLETE state with an empty/pre-copy overview, despite the current nominal regression and all 35 saved native passes. Another variant lets the older read clear loading before the post-copy refresh finishes, re-enabling actions prematurely. Stale failed reads likewise have no generation-scoped error publication.

**Fix:** fence the complete metadata-refresh operation, including selected overview, discovery, loading and errors, with a current refresh generation in addition to navigation identity; invalidate pre-copy snapshots when durable outcomes arrive. A stale operation must neither replace newer metadata nor clear another operation's busy state. Add a deferred snapshot-return test: start a refresh during copy, capture the old overview, complete copy and its new refresh, then release the old snapshot and assert exact saved page IDs/counts and settled state remain current. Also test the reversed finish order and stale read failure. Do not add delays or weaken the existing COMPLETE/idle native assertion.

### Important — LIBRARY-I3: an unrelated read failure can reopen result admission while the original consumer is still running

**Evidence status: true by control flow; not a claim that the retained blocked-provider test failed.** Locations: `app/src/main/kotlin/app/pristinepage/library/ImportLibrarySession.kt:77-85,97-106,130-148`.

Every asynchronous action shares `failed`. If Refresh/Open fails while an import consumer is blocked, `failed` sees COPYING and changes it to INTERRUPTED even though `copying` is still active. `consume` accepts another same-request callback in INTERRUPTED and overwrites `copying` with a second Job. A subsequent Cancel fences metadata, but captures and joins only that second Job; the first provider consumer may still be blocked when the state becomes CANCELED/request=null. Existing SourceStore serialization/idempotence can prevent duplicate durable pages, but does not make joining the replacement Job terminate the original Job. This defeats both duplicate-in-flight admission and the explicit requirement never to claim blocked IO ended from metadata alone. Even without redelivery, an ordinary metadata-read failure falsely labels a live import interrupted.

**Fix:** scope failures to the operation that failed. Metadata errors must not demote an unrelated live copy/cancellation. Bind the active consumer to its request/operation identity and refuse duplicate delivery while it exists, independently of a presentation enum; cancellation must retain and await that actual consumer. Preserve the existing failed-abandonment retry behavior, but apply it only to the failed abandonment operation. Add a host test with a blocked first delivery, unrelated list/load failure, duplicate same-request event and cancellation; assert one delivery/consumer and no CANCELED state until the original consumer exits. A consuming native variant can reuse the existing blocked-provider fixture without inventing a second engine.

### Important — LIBRARY-I4: a valid-shaped but missing saved BATCH permanently blocks import in the retained session

**Evidence status: true by direct fail-closed error-path tracing; no new damaged-state/device experiment was run.** Locations: `app/src/main/kotlin/app/pristinepage/MainActivity.kt:93-97`; `app/src/main/kotlin/app/pristinepage/library/ImportLibrarySession.kt:19,97-108,118-127,141-148`; dependency `data/src/main/kotlin/app/pristinepage/data/repository/RoomImportSessions.kt:153-154`; disabled action `app/src/main/kotlin/app/pristinepage/library/LibraryScreen.kt:35-37`.

An opaque UUID in saved state is syntactically accepted even if no corresponding BATCH exists, or it names an ITEM instead. The session retains it as INTERRUPTED; loading a healthy selected document does not reconcile that request. Cancel reaches the correct repository refusal SESSION_EXPIRED, but `failed` keeps the request and returns to INTERRUPTED. Repeated Cancel/Refresh and navigation to a different healthy document cannot clear it, while Import is globally disabled whenever request!=null. The displayed unavailable/expired message offers reselection, but no enabled action can reach reselection in that session. This is not the corrected ordinary expiry case: an existing expired BATCH can be abandoned, whereas an absent/wrong-kind identity cannot.

**Fix:** provide an explicit safe expired-request recovery/dismissal path after authoritative absence/wrong-kind reconciliation and after proving no local consumer remains. Clear only the unusable UI request; preserve every genuine durable pending batch, committed page/original and unrelated document. Do not treat transient STORAGE_FAILED as proof a request is absent or silently allocate a replacement. Add valid-UUID missing-row and wrong-kind saved-identity tests that end in an actionable healthy library/reselection state without provider IO; retain syntactically malformed-ID and existing expired-BATCH cases.

### Minor — LIBRARY-M1: pagination does not virtualize the growing visible library

**Evidence status: true static complexity observation; no ANR, frame-time or device memory measurement is claimed.** Locations: `app/src/main/kotlin/app/pristinepage/library/LibraryScreen.kt:31,73-78`; `app/src/main/kotlin/app/pristinepage/library/ImportLibrarySession.kt:111-115`.

Every More action retains all prior summaries, and the scrollable Column eagerly composes every loaded document button. There is no document-count ceiling; paging the SQL in groups of 50 therefore does not bound UI composition/retention. List concatenation and owned copying also grow with the accumulated list. This is not the old CATALOG-I1 SQL sort defect, which is corrected; it is a separate eventual UI scalability concern.

**Recommendation:** use a lazy list with stable document/page keys as the smallest improvement before extending this library UI, and define/test the desired loaded-window/scroll restoration behavior if very large libraries become a supported envelope. Preserve prior metadata on errors. Do not claim a measured freeze or introduce a schema/dependency change solely from this static observation.

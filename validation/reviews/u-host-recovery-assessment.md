## Windows semantics and ABI assessment

**True, documented:** `WaitForSingleObject(handle,0)` is an immediate state check. With a valid process handle and `SYNCHRONIZE`, zero is `WAIT_OBJECT_0` (signaled),258/`0x102` is `WAIT_TIMEOUT` (nonsignaled), and `0xFFFFFFFF` is failure requiring GetLastError [W1]. Therefore258 is neither an access-denial error nor the process's exit code. A process becomes signaled at termination [W4]. Creating/retaining an observation handle can keep an already terminated process object allocated, but does not keep that object nonsignaled; merely closing handles is not an established remedy for the observed258 [W3,W4,W8]. INC006's signaled-but-openable situation is materially different.

**True with an important limit:** `GetExitCodeProcess` returns termination status; Microsoft normally describes STILL_ACTIVE259 before termination and an exit/exception value afterward [W2]. Status1 would ordinarily suggest termination, but it is not itself the synchronization object's state. `TerminateProcess` is expressly asynchronous for an external caller, requests pending-I/O cancellation, and cannot complete process exit until that I/O completes or cancels; Microsoft explicitly directs callers to wait to be sure [W3]. In this saved contradictory/intermediate combination, status1 is not sufficient to override a correctly obtained nonsignaled wait. It also does not identify a failed JUnit assertion, application error, pending-I/O handle, or the origin of the value; it could be the termination-request value. The exact original invocation was not preserved here, so that origin is unverified.

**True, available helper audit:** `run_picker_adapter.py` lines59–66 and100–117 declare OpenProcess arguments `(DWORD,BOOL,DWORD)` and pointer-sized HANDLE result, WaitForSingleObject `(HANDLE,DWORD)` with DWORD result, GetExitCodeProcess with DWORD output pointer, and GetProcessTimes with four FILETIME pointers. It opens `0x1000 | 0x100000`, namely `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`; those rights cover both supported status/time reads and waiting [W1,W2,W5,W9]. The unspecified restypes of its BOOL-returning functions use ctypes' default C int, which matches32-bit Windows BOOL; no evident truncation bug is present in these declarations. It checks return success, accepts only wait0/258, and closes its own handle in finally. Its field named `running` means nonsignaled, not independently measured thread activity. I inspected the code but did not instantiate this operational runner or call any of its methods. The exact inline code which produced the original JSON was not retained among the inspected files; helper correctness cannot certify that separate invocation's every declaration, requested mask or handle lifetime.

**True, in-memory layout check only:** this interpreter has8-byte pointers. Defining native Basic fields as signed32-bit ExitStatus, pointer, size_t, signed32-bit BasePriority, size_t PID and size_t parent gives Basic size48 and offsets0/8/16/24/32/40. Prefixing size_t Size and appending uint32 Flags gives Extended size64 and offsets Size0/Basic8/Flags56, including trailing alignment. These exactly reproduce the saved layout and Microsoft documents the Basic field order [W6]. Status0, returned64bytes and matching PID/parent are additional consistency evidence against an obvious layout shift. No native query was executed for this check.

**Uncertain/limited:** Microsoft warns that NtQueryInformationProcess structures are internal and subject to change; the inspected official reference documents Basic, not a stable public Extended flags contract [W6]. Consequently rawflags4's “deletion in progress” label remains supplementary platform-specific interpretation from the coordinator's schema, not independently established official completion semantics. Even accepting that interpretation, deletion-in-progress is not deletion-complete. Neither the extension nor its exit1 constitutes a second independent termination proof: Basic ExitStatus is documented as the same value returned by GetExitCodeProcess. Do not substitute an unverified extended bit for the public wait.

## Alternative recovery assessment

- **Passive natural completion:** permitted and least disruptive; may release the gate without intervention. There is no known safe maximum wait or guarantee of progress. This assignment explicitly excludes polling, so no polling loop, background waiter or further Get-Process was started.
- **Repeat Gradle `--stop`:** no justified benefit once the exact daemon is already signaled; cannot prove or force its child worker's completed teardown. Gradle documents stop as a daemon operation, and Windows does not generally terminate children when their parent terminates [G1,W4]. Another Gradle invocation is also excluded here.
- **Repeat TerminateProcess / taskkill / Stop-Process / tree or job-object termination:** forbidden by the current resumption scope and not an evidence-based escalation beyond the already attempted exact cancellation. No support for assuming another user-mode request resolves a pending-I/O completion requirement. Broader/tree targets risk unrelated processes; parent death alone demonstrably did not reconcile this worker [W3,W4].
- **Close observation handles or restart OpenCode/transport:** closing only one's own completed observation handle is normal resource hygiene, not process termination [W8]. No particular harness pipe/handle was identified as the blocker. Closing arbitrary remote handles or restarting the harness could lose unrelated work and alter process/I/O state; not a justified or authorized recovery here. Preserve the remaining original-handle evidence rather than discard it to make the PID disappear from one view.
- **CancelIoEx / CancelSynchronousIo / suspend-resume / injected exit:** process/thread mutations, outside permission. CancelIoEx cancels issuing-process I/O, not an arbitrary remote worker merely because its PID is owned [W7]. CancelSynchronousIo needs a particular thread handle with THREAD_TERMINATE and requests cancellation without waiting for completion [W11]; neither the relevant thread/operation nor guaranteed driver support is known. These are not safe diagnostic-only substitutes.
- **New worktree/cache/JDK, manual JUnit or another test task, lower worker count, longer deadline:** would bypass the explicit sole-slot gate without proving cleanup. Gradle's Test task still uses a separate forked JVM; `--offline` is not a prohibition on its localhost IPC, and `--no-daemon` can still require a single-use daemon for JVM settings [G1,G2]. Matching client JVM options might avoid that daemon but not the forked test worker. No cache-corruption, version or deadline fix is established. Do not spend another build/probe to rediscover the same uncertainty.
- **Firewall/security/VPN/driver/service changes, network-stack reset, elevation or debugger/dump:** not authorized; impact exceeds this worktree and no component has been causally identified. Debugging may be useful only under a separately bounded operator-approved diagnostic plan, not as assumed repair. Do not disable protections speculatively.
- **Operator-controlled Windows restart:** possible practical fallback if natural teardown does not complete and the operator elects it after saving unrelated work. It affects the whole machine and can interrupt other sessions; the agent cannot establish that it is safe while the operator is away. No automated restart, forced logoff or forced power-off is justified. A restart is host recovery, not proof the original transport/driver cause is fixed.

## Findings — coverage gaps only

### L-M1 — shared-budget test saturates admission before the engine-specific boundaries

**Minor; true coverage limitation, not a demonstrated accounting defect.** Location: `ApplicationCompositionTest.kt:178-183`, in relation to the correct construction at `ApplicationServices.kt:60`.

Cause and effect: filling the entire remainder makes the second request fail at the first positive parser/decode reservation. It proves that a retained renderer result is charged to the shared allowance and subsequent rendering cannot escape that early allowance. It does not independently falsify an accidental future budget split inside GeometryEngine, or prove the geometry-versus-appearance admission boundary under partial pressure. A wrong geometry budget could still leave this all-full test green because decoding would refuse first. The inspected implementation passes the same object to both engines, so this is not evidence that such a split exists.

Witness: `AndroidSourceInspector.kt:49` reserves parser bytes before decode; with `usedBytes == capacityBytes`, it refuses before `DefaultRenderCoordinator.kt:73,87` reaches either engine. This is a source-level witness of the test blind spot, not an executed failing product reproduction.

Minimal remedy: optionally add two small graph-renderer pressure cases using the already imported synthetic source. Leave enough budget for parser and the full retained DecodeAdmission permit, but one byte less than source-plus-geometry; require failure at the geometry stage. Then leave enough for source-plus-geometry but one byte less than source-plus-geometry-plus-appearance; require failure at the appearance stage. Require zero residual charge and intact source after each scope. Use the existing admission estimates and stage records, not a new allocation policy, budget API or large/OOM fixture. Parent may explicitly defer this regression hardening with the source-verified same-object construction as rationale.

### L-M2 — concurrent identity and canceled initialization are not exercised together

**Minor; true interleaving-coverage limitation, not a demonstrated mutex/retry defect.** Location: `ApplicationCompositionTest.kt:189-196` and the separate cancellation case at `:225-242`, in relation to `ApplicationServices.kt:41-53`.

Cause and effect: twelve `async` callers check stable identities after completion, while the latch-controlled cancellation fixture has one requester and performs its successful retry afterward. Neither forces another live caller to be waiting on the initialization mutex while the initializing caller is canceled, nor cancels only a queued waiter while the initializer survives. Thus a future regression in wait/cleanup/publication interaction could evade these separate cases. The present mutex, cleanup and constructor path show no such defect; single-thread runBlocking scheduling is not itself incorrect concurrency testing.

Witness: the concurrent case has no gate on `beforeFiles`; the canceled-initialization case joins its canceled request before making the next runtime call. There is no retained native outcome for the combined schedule. This is an absent test witness, not an assertion that the current graph is duplicated or leaked.

Minimal remedy: optionally extend the existing private fixture with a bounded latch schedule: hold the first initialization in its existing IO hook, enqueue additional live `imports()` callers, cancel the initializer, release the hook and assert surviving callers obtain one graph/renderer and can use the reopened store without provider IO or budget residue. A complementary queued-waiter-only cancellation can assert the initializer and other callers remain usable. Reuse existing services/cleanup; do not move initialization into a new process scope, add an executor or change production cancellation semantics merely to satisfy this test. Parent may explicitly defer with the current source-level serialization/cleanup reasoning.

## Reasonable user failures considered

- Concurrent screens/recreation: production retains one Application services root; repeated graph access cannot manufacture another renderer. No Activity closes the shared store in inspected production call sites. Tests close only their private fixture stores.
- Recovery storage faults or cancellation while opening: existing failure-only, NonCancellable off-Main cleanup remains the path to retry; the new synchronous property does not run before store protection or cache a failed graph.
- Permission loss after completed import: rendering uses committed private bytes, not a renewed provider grant. The new consumer forbids provider reopening. Missing/corrupt private sources or changed conversion identities continue through the existing decoder's typed failure/no-result cleanup; L did not change that policy.
- Low shared allowance while an output stays visible/retained: the whole result keeps its reservation; current new test is designed to refuse a second request without corrupting that first result. L-M1 limits which internal pressure boundaries this directly demonstrates.
- Cancellation while queued/rendering or at dispatcher delivery: the stable coordinator reuses its existing cancellation-aware mutex/checkpoints and completed-but-undelivered owner cleanup (`DefaultRenderCoordinator.kt:22-42`). No additional asynchronous wrapper/queue weakens it. Those existing K behaviors were traced for composition compatibility, not numerically re-reviewed.
- Stale recipe/page/source, result-image retention past close, or store close while another consumer runs: the service does not authorize these. No currently enabled production editor/save/export caller was found that misuses those lifetimes. Future consumers must retain a valid source owner, validate page/revision/generation on publication and close the whole result. Adding a service property alone is neither proof nor a bypass of those obligations.

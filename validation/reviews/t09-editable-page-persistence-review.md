### N-I1 — the newly enabled save path bypasses raw recipe guards before Room narrows/materializes the current revision

**Important; true on the inspected source and generated Room projection.** Exposure: `app/src/main/kotlin/app/pristinepage/ApplicationServices.kt:45` now supplies `ClassicalRecipeAdmission`; `data/src/main/kotlin/app/pristinepage/data/repository/PrivateImportStore.kt:50-53` passes it to the actual `RoomDocumentRepository`. Cause: `prepare` directly calls `q.page` and `q.recipe`, and `verifyLive` directly reads the recipe again. Neither invokes `recipeReadIsBounded` before that projection. Generated Room code uses `_stmt.getLong(...).toInt()` for `recipeSchemaVersion` at line588 and `getBlob` at line590. Consequently the subsequent `decodeRecipe` check sees an already narrowed schema and an already allocated BLOB. The new reader correctly avoids this, but it is a separate port, not a mandatory wrapper around `documents.saveRecipe`.

Bounded witness for parent reproduction, not executed here: import an ordinary valid page at revision1, retain its valid canonical v1 bytes/hash, then update only its raw `RecipeRevision.recipeSchemaVersion` to INTEGER `4294967297`. Call the Application-backed `saveRecipe(pageId,1,validSourceBoundTurnedRecipe)`. The generated conversion produces Int1; current-byte decoding/hash checking and the new classical admission all succeed; `verifyLive` reads the same alias as Int1, then `append` publishes revision2/documentRevision+1. In contrast, `editablePages.load` rejects this exact raw value using the scalar guard. The inspected scalar arithmetic independently confirms the low32 bits are1; there is no speculative native allocation required for this witness. The exported DDL has no schema-version CHECK preventing the stored value, as also reflected in the existing native reader adversary at `EditorPersistenceIntegrationTest.kt:59-66`.

Effect: direct Apply/save can reinterpret an unsupported raw schema as v1 and advance the current pointer where a read-only unsupported/integrity refusal is required. The old bytes need not be overwritten for this to violate the preservation/execution boundary. The same missing ordering allows an over-cap or wrong-storage-class recipe payload to reach Room materialization before codec refusal; the decoder's524288-byte check is too late to protect that boundary. The unsafe projection existed before N; the newly supplied accepting policy makes the schema-alias path reach a successful Application save rather than the factory's default unavailable admission. This is not a demand for map proof, original-byte hashing or memory/output execution admission during saving.

Minimal remedy: reuse the data-owned raw document/page/source/recipe predicates for the save preparation snapshot before the corresponding typed projections, detach only bounded recipe bytes, and recheck the relevant raw validity plus live identity under the existing write transaction before publishing. A preceding successful `EditablePages.load` is not sufficient because the raw row can change before save. Preserve the fail-closed default factory/old bridge, short transactions and codec work outside the write lock. Parent should first retain a small actual Room save regression using `4294967297`, plus a guarded-projection/order witness for a modest524289-byte payload; require structured refusal and unchanged pointers/history/pins. Do not attempt a giant/OOM fixture or add image allocation/map proof to this policy.

### N-I2 — save never authenticates the current revision row's sourceId against its page

**Important; true source-level semantic-integrity defect, independent of N-I1.** Same enabling locations: `ApplicationServices.kt:45` and `PrivateImportStore.kt:50-53`. Relevant inherited implementation: `RoomDocumentRepository.kt:381-397,400-412,416-423,478-490`. Correct contrasting reader check: `RoomEditablePages.kt:46-48`.

Cause: preparation decodes `current.canonicalRecipe` but does not compare `current.sourceId` to `page.sourceId`. `checkBinding` validates the submitted recipe against the Page's Source, not the retained current revision row against that Page. In `verifyLive`, current schema/hash/bytes are compared to preparation, but `current.sourceId` is again omitted. The new scalar recipe guard alone cannot fix this: it bounds the sourceId's type/length without asserting page/source identity. The database has separate Source foreign keys; it does not require RecipeRevision.sourceId to equal Page.sourceId.

Bounded witness for parent reproduction, not executed here: import valid pages using Source A and another existing Source B. For page A's current revision, change only `RecipeRevision.sourceId` to B; keep its canonical recipe bytes/hash bound to A. Both UUIDs/FKs remain valid. Submit a supported recipe bound to A with the actual current revision. `prepare` accepts the canonical current bytes, `checkBinding` accepts the submitted A recipe, admission returns null, and `verifyLive` sees unchanged schema/hash/bytes. `append` writes a new A-bound revision and advances the document even though the current retained revision was internally contradictory. The new reader would correctly refuse the same starting state at line48. No provider, map failure, deletion, race or huge value is needed.

Effect: the now-enabled Application save silently moves past inconsistent source/revision history rather than returning INTEGRITY_FAILED. CAS authenticates the revision number but does not establish that the revision belongs to the page's source. Existing history/source ownership records can remain inconsistent while the command reports Saved. This is not a request to use lookup as a GC lease or to perform file proof inside Room.

Minimal remedy: validate the complete current revision identity, including row pageId/revision/sourceId and its decoded source binding, during bounded preparation, and repeat the current-row source equality/live checks inside `verifyLive` before any insert/pin/pointer write. Retain the existing live recipe/source CAS and immutable history. Parent should first add a real Room save case with a valid foreign SourceId and unchanged canonical bytes, asserting INTEGRITY_FAILED and unchanged document/page/revision/reference/Undo state. A second narrowly controlled preflight-to-commit source-row-change case would protect the transactional recheck. Do not silently repair/rebind the old revision.

# OCR job read boundary — OCR-JOB-READ-07

On `d2543c9`, the existing `Job` table and lease DAO provide a read-only prerequisite for the future OCR owner. The caller must provide a trusted v2 binding and already be in the same database transaction. A scalar query for one exact job ID distinguishes no row from a present row that fails admission. Only a passing scalar permits Room to materialize the job. The reader then compares the exact key, digest and canonical bytes; an equal-length payload and unchanged stored digest are not sufficient.

The largest canonical v2 input is 3,532 ASCII bytes: the maximum-width header and count, plus 32 entries with up to 32 code bytes, 64 hash bytes and two separators per entry. Admission also requires a BLOB of the exact expected extent, null export association and checkpoint, a known state, a stored attempt count of 0–3, bounded owner and error fields, and integer audit timestamps. The UUID is checked after its owner field is bounded. This does not authorize the next start, prove an owner is alive or dead, establish a current page or source pin, or commit text. The consuming transaction must independently establish these conditions. Error values in the generic job row are not yet approved for display or diagnostics.

The four host witnesses failed before implementation because the OCR-only scalar query was absent. They now pass against the actual DAO SQL on exported Room DDL. With the additional state-vocabulary witness, `python -B -m unittest discover -s validation/storage` passed 158 tests. The strict-offline build executed 788 passing data JVM tests (zero failures, errors or skips). Its Android test compilation exposed a test-only `use` call on a Room database that does not satisfy `Closeable`; the fixture now uses explicit `try/finally` close. The focused Android witnesses cover absence, transaction requirement, v1 refusal and same-extent byte mismatch, but Android execution is not authorized in this slice.

Independent persistence review found no Critical or Important issue. It independently reran all four focused host checks, verified indexed primary-key lookup for both queries, and checked embedded-NUL and noninteger refusal and the exact maximum extent. Its one Minor is deferred to the first native owner/lease integration tests: witness a bounded but noncanonical UUID being refused by the Kotlin reader, and verify valid owner/deadline and retained error fields through the generated Room projection. The reviewer did not qualify Android execution, source/current-generation authority, retries, scheduling or completion. The extent cap bounds what reaches the typed projection, not SQLite's internal work to examine malformed stored values.

A second independent review identified an Important integration ambiguity: the reader refuses generic `WAITING_RESOURCE`, `RETRYABLE`, `INTERRUPTED`, and `CHECKPOINTED`. No existing OCR writer produces these states. The [OCR contract](../../docs/specs/OCR_SEARCH.md#implementation-and-acceptance) now explicitly binds the narrower vocabulary and maps queued deferral, restart, and exhaustion without treating old-owner uncertainty as recoverable. An actual-SQL witness pins both the admitted states and the rejected generic alternatives. No production change or added recovery claim follows. A full-capacity Kotlin codec-to-SQL witness and the additional Android raw-metadata controls remain coverage follow-ups.

The focused strict-offline `:data:compileDebugAndroidTestKotlin` rerun passed after the fixture-only correction. No APK was assembled or run in this reader slice; the Room schemas and existing lease writers are unchanged.

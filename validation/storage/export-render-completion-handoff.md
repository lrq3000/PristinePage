## What changed, how and why

- **Actual provenance, not a description of how to render:** Rebuild the exact ordinary request from the verified immutable page and compare it to the borrowed result, including generation zero, source/page/revision/recipe, no protection mask, `FAIL`, and `EXPORT`. Require `OK`, actual RGB dimensions equal the admitted output, a bounded connected stage list with accepted completed outcomes, no stage provider for this empty-provider profile, and bounded stage and result warning codes. Record the actual stage IDs, versions, outcomes, dimensions and warnings in supplied order; no inferred stages, outcomes or timings. At most 16 stages, at most 16 warnings per list, and at most 128 ASCII code characters per string. No raster or result owner is retained in the envelope. Streaming from the borrowed immutable RGB uses at most 12,288 bytes of scratch and cooperative checkpoints, not a second raster copy.
- **Execution format:** Write ASCII domain `pristinepage-ordinary-render-execution-v1` followed by NUL. Use big-endian integers and unsigned-sized positive string fields represented as a 32-bit byte length plus ASCII bytes. Encode the pre-execution key, page/source/blob IDs, source byte and normalized pixel SHA-256, BE64 recipe revision, recipe SHA-256, requested BE32 width/height, purpose, fallback, actual status, actual BE32 width/height, BE32 stage count, then each stage's ID, BE32 version, outcome, input and output dimensions, BE32 warning count and ordered warning fields. Follow with the ordered top-level warning list and actual raster digest field. The canonical job key binds the verified mask/asset/runtime profile and canonical recipe bytes. The raster digest is SHA-256 of `pristinepage-ordinary-render-rgb8-v1` + NUL + BE32 width/height + active RGB rows in row-major order without padding. Cache key is `render-cache-v1:` plus the SHA-256 of `pristinepage-ordinary-render-cache-v1` + NUL + the fixed-format canonical `page-render-v1:` key + execution SHA-256 in ASCII. Attempt, lease, timestamps and snapshot/ordinal do not enter either new identity. Source ID/blob/byte binding records the actual frozen original; normalized-equivalent aliases remain a separate terminal-reader concern, not permission to change the original JOB pin or adopt another row.
- **Trusted file boundary:** Keep existing v1 input, 615-byte intent, and readback seal metadata bytes. The readback must semantically validate the complete closed lossless container and obtain the raster identity independently from decoded RGB. Compare that returned digest with the actual borrowed image digest on write and replay. The existing executor binds it into the seal and checks all surviving encoded bytes; an exact `MOVED` re-verification requires the exact final, not a remaining stage or existence check. Add checkpoints between recovered seal authentication and path work, upon return from semantic verification before re-resolving paths, and before channel opens. After the exact `MOVED` fence the executor alone constructs a receipt bound to its intent authority and to that synchronous thread and callback lifetime; completion consumes it once. Caller cooperation is still required, and readback is trusted and read-only by contract rather than enforced at the OS boundary. The fixture readback is synthetic, not a codec.
- **Atomic metadata:** Compose same-database participants through the existing transaction helper, using one internal guarded path and the same `JobLeaseFence` predicate and lease update. Admit the bounded real job before typed extraction, check the full verified immutable job plus attempt and exact original JOB pin, sample current local liveness/elapsed time/coroutine, and recheck the bounded exact `MOVED` journal binding and audit version. Scalar indexed probes refuse any render ID/job/cache/path collision without materializing the conflicting row. Insert with no replacement, CAS the exact `MOVED` journal preserving the v1 payload and seal triplet, re-admit and match the live job, CAS `SUCCEEDED`, then verify the exact stored journal, render, terminal job and pins. Only after the last SQL statement check original unconsumed lease evidence again against fresh local time/liveness and active coroutine. Any mismatch or late CAS failure throws inside the one metadata transaction. This worker does not change the existing lease clients, public scheduling API or Room schema. No file IO, codec, large raster hash or external checks run in that transaction.
- **Failure and replay:** Refusal after metadata work leaves no published render or success; exact `MOVED` final/seal are kept for same-attempt re-verification. Do not clear retained pins or try to adopt, repair, replace or delete a conflicting row or file. Cancellation after the last observation but before delivery remains distinct from a cancellation already observed in the transaction. Filesystem effects, local samples and SQLite commit are not atomic with each other. `COMMITTED` with a consumed lease is not an input to this command; a separate assembly consumer will read, authenticate and retain terminal evidence.

**Finding and scope:** `U-RENDER-COMPLETE-R` found one Important issue on exact fix base `5b16fc1d0ef483092c97a0297b2429a98931994b`: an execution with the same request and RGB but different stage or warning provenance could be substituted after a late metadata rollback. **Design:** Treat `RoomRenderCompletion` as a caller-retained single-attempt scope. The scope fixes its executor (including the private store and journal authority) and captures the exact lease and intent alongside the original detached execution. The executor first admits the exact journal phase under the live lease, then binds the record only after its fresh `INTENT → COPYING` transaction returns successfully, before opening the stage or invoking the writer. An unbound scope refuses any pre-existing `COPYING`, `SEALED` or `MOVED`; a bound scope will not start a second copy, switch intent or lease, or use a changed execution envelope. Concurrent reuse of the same scope is refused. A matching retry re-verifies the sealed bytes and semantic raster with the existing live file fences and sends only the original producing execution on the executor's synchronous `MOVED` receipt to the metadata join. The scope retains that record through metadata rollback and coroutine cancellation but does not retain the raster, result owner or caller callbacks. It does not outlive the caller's cooperative exclusive ownership. A file-only executor still moves and verifies files exactly as before, but issues no completion receipt. There is no registry, extra metadata transaction, new durable association, SQL/schema change, or change to v1 job input, intent, execution envelope or seal bytes.

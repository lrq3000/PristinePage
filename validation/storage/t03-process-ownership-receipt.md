## Mechanism selection and limitations

Inspected official Android [FileLock](https://developer.android.com/reference/java/nio/channels/FileLock) and [FileChannel](https://developer.android.com/reference/java/nio/channels/FileChannel) documentation2026-11-15 through Svipall. FileLock validity ends at explicit release, channel close or VM termination; exclusive locks exclude another overlapping lock. FileChannel.tryLock is nonblocking, returns null for another program's overlapping lock and throws for other failures. Locks are advisory and VM-wide, not same-VM thread mutexes; some systems release all same-file locks when any channel closes, so the documentation recommends one unique channel per file. These passages establish an API mechanism/caveat, not actual Windows/Android filesystem or process-death acceptance. One cursor restart returned broader material; subsequent same-query pagination inspected the decisive tryLock paragraph. No artifact/runtime/model download occurred.

Coordinator call: use one immutable opaque process-token lock per app-private ownership root, retained by one VM-wide strong reference/unique channel for that process's lifetime. Before exposing an operation owner to any job, persist a bounded exclusive-created record mapping that owner to the process token. Existing structured local scopes still provide immediate local ALIVE/ENDED evidence. A suspending explicit probe outside Room reads only exact validated ownership records and attempts the old foreign process's lock; successful exclusive lock plus matching initialized process marker can populate bounded positive ENDED cache. Missing/unsupported/corrupt/inaccessible evidence remains UNKNOWN; a currently locked foreign process blocks takeover. Never probe/open a second channel for the current process's lifetime lock, never close that live lock through operation cleanup, and never create a missing record during a proof lookup. No PID/date/heartbeat/expired lease is used as termination proof, and no legacy owner without a record gains invented evidence.

Alternatives rejected: PID/name/timeout polling can misidentify reused/restarted/slow owners; per-operation lock channels create avoidable close/reopen/overlap hazards and more descriptors. A dedicated process lock deliberately blocks proof of an old remote operation's end while its process remains alive, unless local structured evidence is available; this is a safe conservative limitation. Advisory locking depends on every application writer honoring the protocol on local private storage, not a claim against a compromised OS or malicious same-UID file mutation. Missing rights/files/native support must block, not silently downgrade. Retain all ownership/fixture evidence; no deletion or schema migration is proposed. The cost if wrong is additional native-protocol work and reopened recovery acceptance, never timeout-authorized publication.

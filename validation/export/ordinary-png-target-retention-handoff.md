## Motivation and achieved boundary

Neither a live requester nor verified COMMITTED metadata keeps a render final from competing cooperating file operations. The plain terminal PNG read still requires its trusted caller to pair the authenticated page with its ordered job and retain the exact stable store, transaction and target for the entire read. It was not changed to grant ownership.

- **Exclusion, not liveness:** `FileOperationOwners`' existing canonical-root pool now also supplies a nonblocking local lane and one fixed `ownership/ordinary-derived-v1.lock` with an exclusive native `FileChannel.tryLock`. Local contention stops before opening another channel. Native `tryLock` returning null is retryable contention; invalid path, unsupported/failed lock (including unexpected overlap), or other unknown acquisition state refuses as a storage failure. Only a regular, nonredirected marker is opened or created, with no writes, replacement, truncation or unlink. The pool mutex is independent of requester liveness and the terminal cache monitor. Scoped operations do not mint more owner markers; an already acquired renderer continues to rely on its existing requester/lease fences. This is cooperative exclusion under a stable app-private root and parent, not protection against unrelated same-UID filesystem access or root replacement.
- **Writer participation:** The real direct `RoomRenderFileExecution.execute` and `VerifiedMoved.Attempt.completeWithCheckpoint` enter that lane before the phase transaction or any target I/O. Completion holds the lane through `commitMoved`; cancellation does not unlock it while structured work is still unwinding. A busy attempt does not open the encoder, advance the file phase or inspect a competing target. Existing attempt/lease checks and journal state transitions are unchanged. The production executor takes one database and requires its file-backed liveness participant to match the files' canonical root; explicitly synthetic test adapters keep the existing transaction doubles. No app wiring.
- **Private issuance and ordinal identity:** The retained terminal reader is constructed from one database and same-root owner/files; the caller does not inject participants at use time. `Prepared` is privately issued and binds its issuing database (exact object identity) and rooted file owner; the terminal reader independently checks both before deriving the page and job from the same validated frozen ordinal. It checks the positive cap and acquires the lane before reading terminal metadata. A private implementation of the typed borrow captures the authenticated render, transaction, seal, size and byte cap and uses the same closed-final authentication and readback as the plain reader. The callback receives no file path, job, ordinal, target or cap selector on the borrow itself. The existing synchronous readback borrows the exact file read-only, as before. Callback return ends the borrow even if its structured children are still unwinding; only after unwind does the lane close. A later scope cannot revive old evidence, and receipt values are not transferable file authority.

**Design trade-off:** A single lane conservatively contends for unrelated targets in one root, while separate roots operate independently. Per-target markers would grow with the inventory. A durable `RenderReference` with a live FK could protect a metadata row but not the journal or final inode without a coordinated reclaim protocol and defined restart/release semantics. It is not a substitute for this bounded slice. When a terminal-relevant mutator is introduced (reclaim, recovery, retention/expiry, replacement/deletion), it must participate or be independently fenced before activating consumption. The low-level `DerivedFiles` API still requires its documented caller ownership; it is not a new general-purpose lock API.

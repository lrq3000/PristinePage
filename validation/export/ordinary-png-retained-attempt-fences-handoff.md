## Motivation and implementation

- **Q-M1:** Before this change, `Acquired` exposed the RUNNING metadata fences directly, accepting only a coroutine context even when there was no continuing store borrow. The two methods are now private. The existing `Retained.readAcquiredSet(acquired)` invokes a final, privately constructed bridge; callers cannot supply an arbitrary receiver or obtain one, and neither the bridge nor the metadata-check operations are returned or passed to the verifier. The only receiver accepts operations from the actual `Acquired` and invokes them inside the existing retained traversal. First verify the original snapshot issuer and exact lifetime through `slot`, then enter that lifetime's retention and the same store's one ordinary derived lane. All entry, ordinal and final metadata work is inside these scopes. This uses private synchronous operations inside the reader across suspending terminal metadata loads, not an externally callable scoped handle, reusable context token, additional lifetime, or arbitrary callback/lane grant.
- Both frozen-content rechecks, bounded job input and RUNNING phase, requester liveness, monotonic deadline and independent wall retention keep their original timing and classifications. The ordinal phase recheck still runs after terminal metadata, again after the compressed scan just before the trusted readback, and after file postchecks. The trusted verifier still gets the existing synchronous read-only exact `File` and a cheap clocks/cancellation checkpoint, not a metadata fence. The original thread-bound final borrow and legacy readers are unchanged; there are no metadata transactions around native/file work. Store close remains nonblocking and refused during retention; no new close or lock-release fault policy.
- **ITEM-JOURNAL-M1:** The primary injectable constructor is private. The normal constructor continues deriving all four participants from one `PristineDatabase`. Independent fixtures use an internal `@JvmSynthetic` factory with an error-level Kotlin opt-in (`SyntheticJournalPorts`) so ordinary Kotlin callers cannot select those ports implicitly. This is test-support marking, not a runtime sandbox against reflection or explicit opt-in. No change to journal read/plan behavior, query order, cap, row identity, payload version, path, or result.

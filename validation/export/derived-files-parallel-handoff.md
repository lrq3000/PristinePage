## Contract and reconstruction

- `DerivedFiles(File, DirectorySync)` takes a stable, app-owned private store root. Its `DerivedFileTarget(DerivedKind, objectId, snapshotId?)` validates canonical lowercase UUIDs using the existing ID validator. The closed RENDER case forbids a snapshot ID and resolves `renders/<objectId>/page.bin`; EXPORT requires a snapshot ID and resolves `exports/<snapshotId>/<objectId>.bin`. Each validated transaction ID binds `staging/<transactionId>/derived.part` and `derived-seal.json`. The internal `PrivateStorePaths` is the existing SourceFiles canonical beneath-root resolver plus directory-ancestry sync, extracted without changing original paths, serialization, force behavior or the source size policy. The old `original.part`, `seal.json` and `sources/<sourceBlobId>/original.bin` remain independent.
- `stage(transactionId, target, maxBytes, writer, checkpoint)` takes a positive caller-admitted Long ceiling, independent of the original-source 100 MiB ceiling. It checks paths and refuses an existing seal before creating a payload with `CREATE_NEW`. The encoder borrows only a synchronous, thread-confined `OutputStream`; it must not send asynchronous writes or retain a filesystem writer. `close()` ends the borrow and is idempotent on the owner thread; the file owner separately forces and closes the channel. Writes are checked against remaining capacity before IO, chunked to at most 64 KiB, and hashed/counted only as successfully written. A swallowed owner-thread write failure still prevents a receipt for a prefix. Empty output, exceptions and cancellation refuse completion. The `StagedDerived` receipt has no staging `File` or descriptor; it binds the canonical store root, transaction, target, byte length and lowercase SHA-256.
- `seal(staged, metadata[, checkpoint])` checks the root and re-hashes the complete closed regular staged file. Copy 1–524,288 bytes of caller-canonical opaque metadata; its domain meaning is not proved by this layer. The separate seal is exclusive, UTF-8 canonical JSON v1 in field order `version`, `transactionId`, `kind`, `objectId`, `snapshotId` (explicit null for renders), `byteSha256`, `byteCount`, `metadataBase64` (standard padded Base64). Force/close the seal and sync its directory before returning `SealedDerived(staged, metadata, sealSha256)`, whose own metadata is defensive and getter returns copies. `sealSha256` is the SHA-256 of the exact UTF-8 bytes, not of decoded metadata alone. No original seal encoding changed.
- `recover(transactionId, expectedSealSha256[, checkpoint])` is read-only. A genuinely missing seal returns null; a present seal must be a regular file, 1–1,048,576 bytes, exactly its observed extent, hash-matched when supplied, bound to the same transaction, and canonical after strict typed decode/re-encoding. A null expected hash is only for a known intent with a lagging journal; the caller must still match the intended target, domain metadata and ownership before proceeding. Zero candidate payloads under a present seal is a refusal. Both recorded copies, if present, must independently be regular, with the same exact expected length and digest; neither can mask same-length drift in the other. The reads are bounded in scratch and linear in bytes authenticated; no whole-payload buffering or broad filesystem search. Inaccessible paths are not treated as absent.
- `move(sealed[, checkpoint])` reopens and independently verifies both the seal binding and every present payload, even if the input came directly from recovery. If an existing final verifies, return it without rewriting or deleting either valid copy. Otherwise retry directory ancestry sync, check again that the target is absent, perform `Files.move` with `ATOMIC_MOVE` only, sync both containing directories and reverify the final. A failed sync can leave bytes at the final path without a success receipt; authorized replay can rediscover and verify them. `finalFile(target)` is a trusted private readback location only: it neither proves existence/integrity nor grants mutation, a pin or readiness. Checkpoints are cooperative, not hard deadlines or rollback on late cancellation. IO/force errors propagate; refused input or corrupt binding does not return a success receipt. `DirectorySync` false means explicitly unsupported; exceptions are not downgraded.

The caller must journal intent and hold exclusive ownership of both transaction and destination, under the exact lease, through IO. Per-instance synchronization is not a cross-instance/process lease. `ATOMIC_MOVE` alone is not an exclusive no-replacement primitive under a race, and canonical checks are not protection against malicious concurrent same-UID writes. Hardening beyond this cooperative, stable-root boundary requires a new review. A non-atomic copy fallback would expose partial bytes; replacing a matching final or cleaning up a duplicate would erase recovery evidence. Neither is done. No hardware/power-loss guarantee, cleanup/quarantine action, schema/job/checkpoint metadata writes, `PRIVATE_READY`, codec/PDF implementation, SAF publication/sharing, signing, device operations, dependencies or settings changes are included.

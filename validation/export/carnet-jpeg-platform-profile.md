# Carnet JPEG/ZIP follow-up — CARNET-JPEG-02

Scope: named JPEG and ZIP export in the Carnet worktree, existing staged-byte/verification/publication boundaries and supported platforms unchanged. Start from the operator-tested four-sided Manual curve checkpoint. No dependency installation, Room schema change, import-profile weakening or PDF activation.

The old export verification reused the import `UNSUPPORTED_FORMAT` error for a different problem: an encoder-owned JPEG with a standard APP2 `ICC_PROFILE` marker was rejected even though the encoder's input was already an opaque sRGB bitmap. The upstream [Android 9 Skia JPEG encoder](https://android.googlesource.com/platform/external/skia/+/android-9.0.0_r1/src/images/SkJpegEncoder.cpp) and its [ICC generator](https://android.googlesource.com/platform/external/skia/+/android-9.0.0_r1/src/images/SkImageEncoderFns.h) show the relevant path, as does [current AOSP Skia](https://android.googlesource.com/platform/external/skia/+/refs/heads/main/src/encode/SkJpegEncoderImpl.cpp). This is a reproducible container-level failure and an explanation consistent with size-independent reports; the operator's exact device encoder output was not inspected. Do not confuse it with source JPEGs that genuinely contain non-admitted color profiles.

Normalize only the explicitly sRGB platform encoder's output, before staging: one recognized single-segment ICC wrapper may be omitted after validating the small matrix/shaper profile (D50, RGB primaries and transfer curves; only the published Skia fixed-point rounding differences are tolerated). Coding tables, scan headers and compressed image bytes are copied unchanged. No profile is stripped from an imported file, no other metadata carrier is accepted by the closed-output verifier, and the strict native decode/pixel comparison still runs on each page. Reject unexpected encoder output as an export verification failure, not a request to replace the photo.

Review and freeze exactly three `android_bitmap` v2 choices: Maximum 100, Balanced 92 (default), Smaller file 80. The choice is independent of dimensions, applies to all JPEGs in the requested ZIP, and is absent for PDF. Existing settings decode without rewriting; copying a ready v1 artifact remains a byte copy, but this writer does not claim to reproduce its v1 encoding. Maximum is lossy and keeps the same verified 4:2:0 chroma policy.

## Reuse and optimization

The inspected Skia encoder already enables optimal Huffman tables (`optimize_coding`). The ZIP writer intentionally does not run DEFLATE compression over JPEG data a second time. [MozJPEG](https://github.com/mozilla/mozjpeg) is the relevant optional encoder: it adds trellis quantization for new encodes and progressive coefficient/scan optimization with `jpegtran`; those are different from stripping a redundant marker. Its [upstream build notes](https://github.com/mozilla/mozjpeg/blob/master/BUILDING.md#building-libjpeg-turbo-for-android) document Android NDK cross-compilation, not a verified PristinePage Android artifact. Do not vendor or add native dependencies for this fix. If measured improvements justify a later approved native spike, compare exact output sizes, preservation of faint text and colors, per-page time/peak memory, ARM64 and 16 KiB compatibility, signed package growth, and retained license notices before selecting a new encoder.

## Verification scope

The host container regression establishes the old classification and checks that normalization preserves other bytes, rejects a different matrix or transfer curve despite the same ICC signature, bounds malformed offsets and refuses unexpected/multipart profiles. The independent review identified the signature-only check in the first revision and a ZIP test that confounded resolution and quality; the first corrected host test run on the initial implementation reproduced both permissive ICC handling and legal-fill rejection. The Android journey covers single-JPEG and album-ZIP selectors, then inspects actual sparse archive names, oriented marks and quantizers in separate fixed-quality/varied-size and fixed-size/varied-quality cases. It does not qualify the largest possible Standard image or every platform profile. Tests, compilation, LDPlayer execution, review of device-specific output and external Save as/Share are separate gates.

The independent follow-up found no new production blocker by inspection and caught that the new whole-album witness was still in batch selection. The witness now exits batch selection before opening the whole-album dialog, independently reads the one synthetic album's `PRIVATE_READY` snapshot and its ZIP entries, and compares actual DQT values to the non-default quality at the same dimensions. A literal prior-settings vector verifies exact historical `android_bitmap` v1 bytes and different v2 identity; actual reuse of a retained v1 artifact, callback failure/cancellation from the native codec, and unexpected post-scan metadata remain separate coverage limits. No new decoder dependency, data migration, PDF enablement or change to publication.

Strict offline Gradle 8.13 passed all five JVM suites (1,408 cases, zero failures/errors/skips), both instrumentation compilations and app lint (zero errors, 21 warnings, one hint). A final `:app:compileDebugAndroidTestKotlin :app:lintDebug` run after adjusting the ZIP journey also passed (1m34s, 123 tasks, five executed). The host storage suite passed 146 cases independently. No LDPlayer run or physical-device operation was performed; actual device encoder/readback, ZIP interaction and Save as/Share are not accepted from these checks.

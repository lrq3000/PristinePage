## Motivation and achieved boundary

Neither a terminal RENDER nor a persisted EXPORT key alone authenticates an assembly item. The new synchronous, internal `RoomPngExportItemReads` is a read-only leaf. Its Room constructor derives the transaction and SQL queries from the same `PristineDatabase`; the caller supplies the authenticated assembly identity, actual owner/generation/attempt, ordered frozen page count, and (only for precommit) the entire ordered plan. The plan supplies the exact planned artifact and EXPORT transaction IDs and the independently observed EXPORT seal for that move, not the seal from the RENDER receipt, a digest recomputed from that receipt, or anything discovered in the EXPORT row. `MOVED` here is metadata agreement with that plan; it is not proof of current files, live authority, or readiness.

- **v1 format.** Owner key: `export-item-v1:<canonical assembly job UUID>:<ordinal>` with unpadded decimal `0..99`; SQL binds the actual attempt separately. The 685-byte payload starts with ASCII `pristinepage-ordinary-png-export-item-v1` plus NUL, then snapshot UUID/hash, assembly job UUID/input hash, lease-owner UUID, generation and attempt (Long), ordinal/width/height (Int), terminal job UUID, render UUID, RENDER transaction UUID/seal, encoded hash/count (Long), raster hash, artifact UUID and EXPORT transaction UUID. UUID and hash text is fixed canonical ASCII; numbers are big-endian. Page count and ordered terminal job IDs are bound by the supplied canonical assembly input hash; the precommit plan independently rebuilds the existing v1 assembly envelope to check consistency before the transaction. The cap is a caller-supplied positive ceiling, not persisted; count must be positive and no greater than the cap. The payload records RENDER provenance, not the later EXPORT seal. The expected EXPORT seal is compared separately against the row.
- **Bounded reads.** Both entries use one short same-store metadata transaction: ask the existing snapshot/ordinal inventory for exactly `n+1` IDs (even `""` is presence), then use exact `(EXPORT, owner key, actual attempt)` scalar seeks up to 100 keys. `FRESH` requires all 100 canonical keys absent, with no typed rows read. `MOVED` requires all first `n` scalar results true and remaining canonical keys absent, then projects only expected keys in ordinal order (at most `n` rows). A Kotlin `null` result is a missing key and `false` is malformed matched storage; neither is permission to project. Even a false hit on an extra key refuses before any projection. A case alias, noncanonical ordinal spelling, another job/attempt or another kind is not included in this proof; this is not a database-wide absence or orphan claim. The projection is an exact indexed seek with an explicit 12-column list, no `SELECT *`, audit timestamp or returned persisted identity. The reader reconstructs `staging/<EXPORT transaction>/derived.part` and `exports/<snapshot>/<artifact>.bin` as identity strings only and checks full payload equality, expected state, seal, encoded SHA-256 and count. No DAO, file, row, or BLOB escapes.
- **Typed outcomes.** `Verdict.FRESH` or `Verdict.MOVED` are metadata observations only. Invalid plan input yields `INVALID_INPUT/png_export_item_invalid_plan`; a valid planned count above the supplied cap yields `RESOURCE_LIMIT/png_export_item_byte_cap`. `INTEGRITY_FAILED` distinguishes `png_export_item_artifacts_present`, `png_export_item_occupied` (well-shaped fresh hit), `png_export_item_unbounded` (raw malformed expected/fresh hit), `png_export_item_missing` (absent expected MOVED hit), `png_export_item_extra` (any extra exact canonical hit), and `png_export_item_mismatch` (typed mismatch or impossible loss of admitted projection). Unexpected read exceptions become retryable `STORAGE_FAILED/png_export_item_read_failed`; cancellation propagates. A raw-bounded but wrong phase such as SEALED still fails typed comparison; this is not same-attempt resumption.

The existing exact-key index and ID inventory are sufficient at the known ≤100-page bound; a prefix scan or separate persistent mapping would either widen scope or duplicate identity. Keys outside `0..99`, historical IDs, other snapshots/jobs and unowned attempts are not searched. Inventory is occupancy evidence only, not artifact ordinal or provenance validation. This leaf does not call `Acquired` fences or revalidate liveness, wall retention, files, or rows after its transaction. A later writer still needs `Q-M1` structural retained-scope fencing and must use checks in the owning mutation boundary, not rely on a detached successful observation.

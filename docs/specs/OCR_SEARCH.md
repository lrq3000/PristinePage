# Background OCR and Home search

## User journey

Search at the top of Home across saved albums, dates, supported source metadata and actual recognized text. Results for text/metadata on a page should lead to that page inside its album; title/dates remain searchable even when OCR is unavailable. Include supported EXIF fields such as captured date, orientation, device make/model and exposure values where safely available. Do not index raw EXIF blobs, private URIs, paths, serial numbers, GPS or unbounded comments by default; distinguish ordinary metadata coverage from sensitive fields. Search only live, visible albums/pages; source sharing by duplication must not expose a removed page. No query history or upload.

When connecting Home to OCR, keep album matches separate from page hits, and recheck a hit just before opening its page. A saved result for a page's old revision, a hidden staging page, or a removed album must not become a navigable search result. Existing title/date matches should remain usable even when OCR is unavailable or unprocessed.

While a text query is active on visible Home, a committed Room result or page-visibility change refreshes its loaded page-hit window without rerunning the album search. The initial subscription also catches commits published between the first query and registration. A failed background read leaves the last window and its continuation intact; exact accepted-revision and producer checks still apply to a tap. An admitted tap is not canceled just because the same guarded hit was presented again. This observation contains no scan text, query history, file paths or job execution authority.

Source-metadata search accepts only explicit selectors: `format:jpeg`, `format:png`, `format:webp`, `orientation:1` through `orientation:8`, and `captured:YYYY-MM-DD` (for example, `captured:2024-02-29`). A bare date or number is not implicitly a metadata selector. Orientation 1 includes sources whose decoder applied no transform because the tag was absent. A valid selector routes only the page-hit stream to metadata; other queries still use OCR, and album title/date matching remains independent. Candidate pages advance through opaque keyset continuations; the exact-page lookup rechecks current membership and the stored source/recipe binding without opening originals or consulting OCR. Camera make/model and exposure are not yet available in this projection.

The capture-date parser prerequisite extracts only the local calendar day from a valid `DateTimeOriginal` in the primary image's directly referenced Exif IFD. It does not infer a time zone, use file times, retain the source time of day, or consider GPS, thumbnails or alternate subimages. Unsupported date values are absent; the existing TIFF envelope and orientation/profile rejection rules still apply. Do not expose a capture-date filter until an authenticated ingestion projection can persist it and distinguish older sources with no projection from sources with no usable capture date.

The capture-day reader seeks the exact indexed Gregorian day and orders matches by original blob ID, then page ID. Several live pages may share one original; pagination must not drop the remaining pages of that original. Recheck the date and original-byte digest alongside the existing live page/source/recipe and Atelier visibility checks before issuing a hit and again on tap. Neither search nor tap reads the original, the ingest receipt or OCR text. The read authenticates the projection against the stored blob identity, not a new proof of the file or its camera clock. Application ingest forwards date-capable inspection through its existing shared decode queue for new imports only. Sources admitted before this wiring have no date projection; the app does not infer or backfill dates. Both ordinary import and Home navigation still require current-build Android evidence.

OCR starts after a page is durably saved, including background backfill of existing pages. An unfinished current saved job with an observed unfinished wake shows a dimmed thumbnail and indeterminate activity indicator in the album. Use “Text recognition queued” for an enqueued wake and “Text recognition pending” for a wake that is running but may still be preparing; WorkManager does not establish that recognition started. A terminal job, a missing or ambiguous wake, or an uncertain read clears the overlay. In the saved page toolbar, **Processing details** is always reachable; show “No errors reported” if none. The app-wide opt-in adds structured diagnostics such as effective engine, input size, preprocessing, stage status and elapsed time. Do not retain raw command output, image data, OCR text, paths, or exception messages inside diagnostics; the separate OCR result is private content.

**OCR text** shows the exact recognized text (including an explicit no-text result), its engine/settings, and whether a previous result is retained during refresh. Offer text export through a user-selected document destination, rerun with defaults or saved per-page settings, and a choice of qualified installed OCR engines. Default settings are inherited only until overridden; no existing accepted recipe or original is modified. Do not export or index synthetic fixture text. PDF text-layer generation is separate.

Read each saved-page panel against the editor's accepted revision, never the unsaved recipe. Processing details reads metadata only; OCR text reads the verified producer's verbatim output only while its dialog is active and does not save it in navigation or instance state. The read-only dialog does not use selectable text or its platform text-classifier/clipboard path; external transfer remains a separate explicit action. The panels are refreshable snapshots, not evidence of live WorkManager progress.

**Settings → Text recognition (OCR) → Show OCR diagnostics** defaults to off and persists only a Boolean. When on, Processing details may show the planned OCR input extent and named requested appearance/finishing from the accepted recipe; the normal status and structured last error remain visible without opt-in. These values are not evidence that preprocessing ran or that a native raster was allocated. Do not substitute editable preview dimensions or fabricate a duration. The opt-in does not enable collection, logging, scan-text access or any external transfer.

The text-export prerequisite issues a private in-process observation with the shown text. Only the same store can resolve it, after rechecking the exact saved input, producing job, canonical OCR intent and digest of the verbatim UTF-8. A new pending rerun does not invalidate the still-displayed producer; a different published producer does, even when it returned identical text. A verified blank is zero bytes, not absence. The observation holds no plaintext or destination, is never saved across process recreation, and does not grant authority to write or declare an export complete.

The private file layer can seal and verify the bounded verbatim byte stream, including a genuinely empty file, separately from image/PDF export. File-layer success does not make the artifact ready, grant destination consent, or establish provider write/readback. See [the private directory layout](DATA_MODEL_AND_STORAGE.md#private-directory-layout-and-identity) for the staged ownership boundary.

The private preparation path now rechecks the displayed OCR observation and records the exact bytes' digest and length together before staging. The store serializes the closed-file seal and move, then issues a private receipt only after the journal's final exact readback succeeds. The receipt exposes neither the original nor a path, document provider, destination, or share grant. Standalone Save as, process-death recovery, and ordinary Android use remain separate acceptance steps.

A prepared receipt is bound to its issuing store instance. To read it, verify the committed journal before and after the exact private seal and file proof, then supply only detached bytes. A later OCR rerun or an amended page does not replace an already frozen artifact. Never hold this private file lane across external provider I/O. The lane may recreate its private lock marker; receipt reads do not write the artifact, seal or journal.

The operator requires multilingual offline OCR: at least 20 languages, including English and French. A two-language bundle is not sufficient. The [size inventory](../../validation/providers/ocr-engine-shortlist.md#multilingual-footprint) compares a cross-script starter set with the provider's full catalog. **Settings → Text recognition (OCR) → OCR languages** saves the ordered default selection (initially English and French), separate from installed models or app language. Show when no engine is active rather than pretending a setting schedules recognition. Changing a default must not remove packs or existing text or start an implicit full-library rerun. The effective job configuration must identify the ordered language selection and installed pack versions so a worker restart cannot silently recognize with different models. Verify real extraction and search by script, including RTL, CJK, and mixed-language pages; pack presence and script detection are not recognition or search acceptance.

## Ownership and limits

Reuse the existing Room store and WorkManager dependency. WorkManager receives only opaque IDs; a transactional row owns current input revision, effective engine/version/config, generation, attempts and output. Capture/append/save and startup reconciliation discover durable pages and unfinished work even if scheduling was interrupted. Execute one inference at a time under the shared image budget, off Main, deferring when necessary so interactive work is not blocked. Never use a new raw copy of photos or a second app-wide allowance. More than one scheduler signal must not create additional attempts. Persist completion and index update together; obsolete generations and deleted/changed pages cannot publish. Force-stop may defer execution until launch.

The initial OCR raster target is the accepted recipe's rotated destination, fitted without upscaling to a 2,400-pixel long edge. It has a separate `OCR` render purpose, shares the normal source authentication and image allowance, and requires `FAIL` rather than an alternate raster. Full source verification and native engine allocations still need measured device fit. This is an OCR input policy, not an export or saved-recipe size change.

The renderer separates an impossible idle-budget fit from temporarily occupied headroom. After committed-byte proof and before codec decode, it estimates the maximum of the parser, decode-plus-geometry and geometry-plus-appearance reservations with the same shared charge formulas. The observation does not reserve capacity. If admission fails later, only a denial by the same ledger whose actual charge could fit alongside the render's own still-held charges can request redelivery. Geometry proof exhaustion and native allocation failures are not classified as transient ledger pressure. The separate bitmap and engine preparation still need their own qualification.

Count each started attempt once, including an abandoned in-flight attempt after its owner is proved ended. Persist the third failure as terminal; no fourth automatic attempt. Manual rerun starts a new fenced generation and retains the prior successful text for the same input, clearly identified, unless the page revision changes. An engine may refuse before execution when unavailable; a missing runtime is not three quality failures. Keep bounded local structured error/step records. A successful empty string means no text detected, not failed extraction. Reject oversized or malformed output rather than silently indexing incomplete text. Test fixtures exercise the pipeline without entering production indexing.

An explicit rerun consumes a status observation issued by the same store. Recheck the live accepted revision and exact predecessor job and canonical intent inside the enqueue transaction. Reusing the same observation must not allocate another generation. Publish only ID-only wake hints after commit. Keep a prior result attributed to its actual producer and do not retire any predecessor pin in the rerun transaction.

## Implementation and acceptance

First implement the engine-neutral transitions and Home title/date search, retaining catalog ordering and pagination and showing which fields are actually searchable. Next bind guarded Room records to the existing live page/revision, add additive migration and SQLite full-text indexing subject to supported API evidence, then connect durable background work and UI status/details. A fake engine belongs only to isolated tests. Evaluate a compact OCR-first default and treat generative transcription as an opt-in comparator, not an automatic fallback. Engine selection, artifact acquisition/rights, OCR quality and latency on representative documents, migrated Android execution, interrupted retries, exact page search navigation, diagnostics, text export, and offline operation are independent acceptance gates.

The first Home search combines terms across titles and both timestamps, accent-insensitive for titles, with the same local English date/time format as cards, plus ISO dates. A month/day and its adjacent year/time, or ISO date with its adjacent time, must match one timestamp rather than unrelated digits or separate timestamps. The field lists its current coverage after text is entered. The query is session-local and must not enter saved navigation, logs or error strings. No OCR, EXIF or other scan content is searchable in this increment. The runner issues a fresh attempt identity per claim; generations and retry ordinals alone are not unique between independently queued snapshots.

The next storage witness must cover v2→v3 with preexisting pages, no OCR text on upgrade until actually recognized, hidden staging/removed/stale entries absent from results, old completion after manual rerun, interruption with known and unknown owner state, and atomic OCR-text/FTS replacement. Prefer a private Room result entity with one row per page and an external-content [FTS4 entity](https://developer.android.com/reference/androidx/room/Fts4) to a second stored copy of plaintext or an unindexed corpus scan; use [SQLite's documented MATCH and synchronization rules](https://www.sqlite.org/fts3.html). Verify the exact generated schema, synchronization triggers and relevant platform SQLite module before activation. If the module is not supported on a required platform, retain the existing catalog and defer activation rather than making every app open depend on an unverified migration. Bind a literal token grammar rather than passing raw text as an FTS expression; bound query length/results, and do not store raw searches. Never treat a match-table row as navigation authority without rechecking live ownership.

The storage increment will establish guarded result/index storage and an additive-migration witness first; it will not expose a production text writer without a fenced owner. Keeping OCR results separate from generic job inputs avoids retaining private text in queue history. The following worker increment should reuse existing job lease and process-liveness primitives under WorkManager: one durable per-page generation with current accepted recipe/source and effective OCR config, indexed bounded reconciliation for missing or obsolete work, and result publication within the same transaction as current ownership verification. New saves must remain independent of unavailable OCR; a separate bounded reconciliation can make interrupted scheduling discoverable. Keep directory/file operations and inference out of Room transactions.

Store one normalized search form and preserve the verbatim engine output when it differs. The displayed and exported text is always the verbatim output, not the normalized index form. Search and storage use the same bounded canonicalization before FTS tokenization. A matching ID is still a candidate until the consuming repository has verified the guarded page and decoded any Atelier promotion receipt.

Word-only `unicode61` matching does not by itself search inside unspaced CJK text: a host FTS4 control matched `東京都の領収書です` as a whole but returned zero rows for `領収書` inside it. Before NFC normalization, fold half-width kana so standard voice marks compose with their base. Segment Han, kana and Hangul runs into code-point tokens and search each unbroken query run as a quoted phrase. Phrase matching is ordered token adjacency, not exact punctuation/whitespace/combining-mark matching. Apply the same projection on OCR result preparation and search, without changing verbatim text, adding a second index or losing the existing word behavior for other scripts. Add a tokenizer version to the rebuild policy before any production results are populated. [ICU dictionary-based segmentation](https://unicode-org.github.io/icu/userguide/boundaryanalysis/#dictionary-based-breakiterator) is a future candidate for Thai, Lao, Khmer and Burmese or for measured ranking gaps; this first step is not universal word segmentation.

For durable work, prefer one current per-page binding pointing to the existing `Job` owner rather than adding an independent lease registry. Bind opaque page/source IDs, current recipe revision/hash, normalized source identity, effective engine/settings and a fresh generation. Use the existing monotonic lease and `FileOperationOwners` proof; a live or unknown prior owner is not taken over just because time elapsed. Deduplicate startup/backfill scheduling, race the third failure against manual rerun, and make same-input rerun retention, changed-revision invisibility, interrupted-attempt recovery and cancellation explicit test cases. A queued job and a previous recognized result are distinct records, so manual rerun need not discard useful text or expose a prior recipe's text as current.

The v1 durable intent uses `Job.kind=PAGE_OCR`, no export snapshot/ordinal, and key `ocr-page-v1/<page-id>/<generation>`. The canonical UTF-8 bytes are NUL-separated fields, without a trailing separator: `pristinepage-ocr-page-v1`, document ID, page ID, source ID, recipe revision, recipe SHA-256, normalized-source SHA-256, work generation, engine ID, engine contract version and layout name. All fields use canonical bounded ASCII. A consumer must generate expected bytes from trusted page/config ownership, admit raw job type and extent before materialization, and verify exact IDs, key, SHA-256 and bytes; that comparison is not job acquisition or proof of a live page. Recognition results, queries and lease/attempt history never belong in these bytes.

The `PAGE_OCR` v2 envelope changes the domain to `pristinepage-ocr-page-v2` and the key to `ocr-page-v2/<page-id>/<generation>`. After the ordered v1 fields, append the unsigned decimal pack count and, in recognition order, each canonical pack code and exact lowercase SHA-256 of its installed recognition data. Use the same NUL separation and no trailing separator. Admit 1–32 distinct pack codes matching `[a-z][a-z0-9_]{0,31}`; do not use an empty list to represent a real installed configuration. The digest is the byte version of the pack, not a release label. Keep v1 available as the existing engine-neutral fixture contract, not a production fallback when an exact pack binding is unavailable. The typed list is detached and immutable. No file paths, OCR data, or authority for download or file access comes from the envelope. A future producer must establish the installed identity before using it and must not fall back to newer bytes after a restart. Pack installation and engine restart do not mutate prior recognized text.

When the stored binding changes, a new job uses a fresh generation, not a replacement at the same key. Persist or link the producing job's exact configuration with each successful result before enabling the worker, so an old result retained during a rerun cannot be attributed to the new job's settings or packs.

Use an additive `OcrPageWork` record keyed by page ID. It holds the current `Job` ID, generation and expected input digest/extent so a restarted reader can do the existing bounded SQL admission before materializing bytes. Keep a separate nullable successful-result job ID and search-projection version in that record. Advance both result provenance fields with the text result in one transaction; advances of the current pointer alone preserve old result provenance. A migrated historical row without a producing job does not become a production OCR result. This metadata table creates no work or pins on migration, and no writer may use it without the live-page and source/lease checks.

The [bounded Room read](../../validation/storage/ocr-job-reader-receipt.md) expects the owning transaction and a trusted v2 intent. An absent job is distinct from a present job that fails validation. The reader does not resolve which generation is current, take a lease, or authorize a retry. Apply the attempt cap before writing a new start under the same transaction; admitting a stored count of three for readback must not authorize a fourth start.

On restart, recover the original ordered pack and engine identities from already byte-admitted v2 job bytes, not today's Settings or newly installed pack versions. The v2 decoder accepts only canonical writer bytes and does not create a trusted binding by itself. A consumer must independently verify the exact persisted job identity, current pointer and accepted page/source/revision in the same database, then resolve and retain the exact installed assets before inference. Never use decoded strings to open files directly.

The v2 OCR reader admits the narrower `PAGE_OCR` states `PENDING`, `ADMITTED`, `RUNNING`, `SUCCEEDED`, `FAILED`, and `CANCELED`; OCR does not persist an intermediate checkpoint. Resource deferral keeps an unstarted job pending or admitted without counting a start. After a failed or positively confirmed abandoned start, the future writer must record the structured error and either return the same generation to `ADMITTED` below the cap or move it to terminal `FAILED` at the cap. It must not write generic `WAITING_RESOURCE`, `RETRYABLE`, `INTERRUPTED`, or `CHECKPOINTED` job phases for this reader. An unknown old owner remains blocked. This defines the intended storage vocabulary, not a working recovery transition.

The sole pre-start terminal resource outcome is `FAILED/PREPARATION_RESOURCE_LIMIT`, with no lease and the original start count below three. Enter it only for the renderer's typed impossible-idle-budget proof after checking the exact saved recipe, original file bytes and recorded source identity, before decoding source pixels or handing off a prepared session. Keep the original JOB pin and any prior producer untouched. A generic resource or native memory failure, a missing provider, current contention, and a stale input cannot enter this state. An explicit rerun or changed saved input can create a new generation; automatic reconciliation does not repeatedly schedule it.

The internal result transaction must recheck the current binding and exact job under the same live lease, store the result, and confirm that the exact expected row exists before commit. A no-op writer cannot mark a job successful. Losing liveness, cancellation, or a late verification refusal rolls back both state and replacement text. Its injectable ports are not production authority: the store still has to supply the current-binding, bounded read and verified write from its own Room database and the registered process owner.

Initial compatibility evidence: AOSP enables `SQLITE_ENABLE_FTS4` in the inspected distribution build definitions for [Android 8.0](https://android.googlesource.com/platform/external/sqlite/+/refs/tags/android-8.0.0_r1/dist/Android.mk), [Android 9.0](https://android.googlesource.com/platform/external/sqlite/+/refs/tags/android-9.0.0_r1/dist/Android.bp) and [Android 15](https://android.googlesource.com/platform/external/sqlite/+/refs/tags/android-15.0.0_r1/dist/Android.bp). A host SQLite CLI 3.50.4 also executed an external-content `fts4` query with `unicode61`; the host Python SQLite 3.51.1 build lacks FTS4. None is evidence of a migrated Room database on LDPlayer, all OEM builds, or actual search indexing.

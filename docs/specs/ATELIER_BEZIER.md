# Atelier cubic contour — mapping prerequisite

This design supplies a small, conservative mapping contract for [Atelier](ATELIER.md). It does not declare a saved recipe, Android UI, or admission for a renderer merely because the pure map works. Keep existing perspective and manual midpoint recipes readable and unchanged.

## Shape and exact parameterization

The four pinned corners are TL, TR, BR, BL in the oriented-source pixel-center coordinate space. Orient the top and bottom chains left to right, the left and right chains top to bottom. Each chain is a continuous sequence of cubic segments with two independently editable controls. A knot owns a strictly increasing normalized parameter; the first and last parameters are exactly zero and one. Cap each edge at 8 segments (32 segments total) and reject degenerate intervals shorter than `1e-5`. Keep shared endpoint identity exact.

Use De Casteljau to split a chosen segment at a local `t` and split its global parameter interval at the same ratio. Segment endpoints and control coordinates define actual cubic output. Inserting a knot preserves the mathematical curve and its parameterization, not necessarily every RGB byte: rounded child controls can cross a byte-quantization tie. Untouched chord insertion remains byte-exact. Moving a handle or knot changes the source boundary; four anchors cannot be removed. Horizontal/vertical destination values use fixed `u,v ∈ [0,1]`. Quarter-turns still compose in destination space before evaluating the map.

## Backward map and conservative admissible envelope

Let `B(u,v)` be bilinear interpolation of the four corner anchors in source pixels. For each edge, define its departure from the corresponding straight corner interpolation: `T(u)`, `Bottom(u)`, `L(v)`, `R(v)`. Each departure vanishes at its corner anchors. Use `F(u,v) = B(u,v) + (1-v)T(u) + v Bottom(u) + (1-u)L(v) + u R(v)`. This Coons patch hits all four genuine cubic edges without fitting midpoint proxies.

For a convex `B`, the Jacobian determinant is affine in `(u,v)`, so its smallest determinant is at a corner. The Jacobian's Frobenius norm is convex, so its largest Frobenius norm is at a corner. Their ratio `m` is a conservative lower bound on the smallest singular value. Along any segment between two destination points the bilinear difference is exactly its midpoint Jacobian times the segment vector; consequently `|B(p)-B(q)| ≥ m|p-q|`. Bound each departure and its derivative using the convex hull of the segment's cubic/derived-quadratic Bernstein coefficients, taking the maximum across pieces with derivatives measured in global edge parameter. A Lipschitz upper bound for the correction is `hypot(max(T', Bottom') + L + R, max(L', R') + T + Bottom)` with each symbol a vector-norm upper bound. Require the correction to be below `m/2`. This conservative margin gives injectivity, prevents orientation reversal along the continuous scaled correction, and rejects unsupported strong shapes instead of approximating them. Widen bounds conservatively or reject near the floating-point limits before relying on this proof to admit production maps.

Bound source support using the corner-box extrema and the component-wise departure intervals; opposite edge corrections are convex interpolations, not an arbitrary sum of both whole deviations. Fail closed if coverage can leave oriented source bounds. Do not clip a map to the image, which can create a fold. Bound stretch and absolute footprints under the shared render policy before adding a consuming raster. The exactly straight case must delegate to the existing perspective path (not a subtly different bilinear warp); pure contour segments may still exercise the map for identity/continuity tests. Validate paired masks through the exact same admitted inverse sample coordinates when supported. Reject clipped, uncertain or resource-exhausted cases with typed errors.

## Readiness for Android consumption

Independent numerical review confirmed the exact-arithmetic injectivity argument, not floating-point certification. Before renderer admission, test the extent envelope on an inward full-frame bow, establish a straight-dispatch test invariant under knot insertion, and measure the transition on a skew quadrilateral: the limit of this Coons candidate is bilinear, not the homography used for the exact straight path. Do not claim smooth editing across that dispatch until the behavior is resolved.

### Projective-base candidate

`AtelierProjectiveContour` evaluates the same corner homography in the interior, adds the cubic-minus-chord departure along each edge, and uses the homography denominator ratio to convert destination edge parameters to source chord fractions. The departure therefore vanishes for straight chains on skew pages without switching to a bilinear base. Host tests cover full-frame inward versus outward deformation, a skew straight page with an inserted knot, a real cubic handle affecting pixels' source coordinates, curve-preserving insertion, and strong-bow refusal.

Independent review confirmed the projective chord identity `H(q) − H(p) = [z(p)/z(q)] DH(p)(q−p)` and the resulting exact-arithmetic no-fold bound. The curved candidate now requires a global outward-rounded proof for the continuous mathematical map with the stored coefficients and edge weights: bound the base Jacobian and derivative norm in active-source-normalized coordinates, subtract the correction's derivative bound from the base's minimum singular value, and apply the shared minimum stretch, maximum norm, determinant and condition limits. This global proof may decline maps that a tighter subdivision could establish; a thin injective crop is not accepted just because it cannot fold.

The same proof bounds coordinate extrema by the four true map boundaries, including each solved corner's residual and the difference between exact and rounded projective edge weights. The evaluator additionally checks minimum and mean bilinear support on the existing 129×129 reference lattice with a cancellation checkpoint per row. Full-source and preview-sized preparations both accept the tested inward full-frame edit. The raster must still guard its actual rounded samples and charge bounded workspace; the proof is about the mathematical function, not an assertion that every floating-point output coordinate was evaluated in the lattice. Untouched chords retain exact zero-departure semantics after a legal short insertion (including `.99998` on an eight-pixel edge); an actual handle edit is never dispatched as straight by tolerance. The renderer must use the existing integer-center perspective raster path for straight chains.

`GeometryRecipe.Bezier` stores `atelier_bezier_v1` with normalized immutable chains, distinct handles and explicit chord state. `GeometryEngine` uses the same certified map for preview and full-target render, precomputes horizontal/vertical departures, then checks the actual rounded coordinate before shared RGB/coverage/protection sampling. The straight path uses native integer centers, including exact full-frame permutations. Local JVM witnesses cover codec reopening, legacy golden bytes, rotated mask alignment and strong-bow refusal. Complete independent review and native saved reopening, accessibility, skewed/dense-knot and resource/cancellation coverage before claiming AT-04.

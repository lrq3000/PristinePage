## Ownership and non-negotiable invariants

`:data` owns Room entities/DAOs, private files, durable journals, repositories, snapshots and recovery. `:image-android` owns decode/render/encode and implements ExportService orchestration against repository/file contracts. `:app` owns URI result routing, CameraX, UI and WorkManager entry points. `:core` remains Android-free and supplies Recipe, OutputSpec, ProviderIdentity and canonical recipe encoding; no Room entity contains Bitmap, Mat, tensor, open file descriptor or live model session.

VERIFIED DOCUMENTATION: Room transaction methods commit their database work on success and fail/roll back on exceptions; transactionally loading related rows yields a consistent database view. This does **not** encompass files moved outside SQLite. [Room Transaction reference, updated 2026-10-26, inspected through Svipall 2026-11-14](https://developer.android.com/reference/androidx/room/Transaction). DESIGN: source/page visibility is delayed until a journaled private file is verified durable enough for the operation; startup reconciliation handles interruptions on either side. Never describe Room plus file rename as one atomic transaction.

- Original encoded bytes are immutable. A normalized image has a separate versioned pixel identity; user rotation changes only GeometryRecipe.outputQuarterTurns and recipe/render identity, not source bytes/hash/binding or source-space controls/masks.
- Each PageId belongs to one document and has an independent immutable recipe history. Document order is a stable ordered list of PageIds, not filenames or image offsets.
- Recipe revisions and document revisions are monotonic Long values, never reused on Undo. UI generation is separate, transient and not a committed-job identity.
- A committed visible page references an existing verified source blob and its normalized source binding. Unknown versions are preserved but read-only/unsupported, not rewritten into a guessed recipe.
- Snapshots and committed jobs pin every required source, recipe, mask and provider asset identity until their explicit retention ends. Deleting an editable page does not mutate a frozen export.
- Refcounts are metadata derived from explicit ownership rows; filesystem presence is not ownership. Reclamation requires a confirmed unreferenced object and a fresh transaction check, never a cached zero count.
- No source URI, original filename, pixel payload or private user title enters logs/WorkManager Data. URIs needed to resume import/publication remain only in private bounded operation records.

## Identifiers, encodings and public repository contracts

All names below are design contracts in the future app. Define model types under `data/src/main/kotlin/app/paperlight/data/model/`, repositories under `.../repository/`, files under `.../files/`, journal/recovery under `.../journal/`, and Room under `.../db/`. IDs are opaque random UUID strings wrapped in Kotlin value classes: `DocumentId`, `PageId`, `SourceId`, `SourceBlobId`, `ImportSessionId`, `ExportSnapshotId`, `JobId`, `RenderId`, `TransactionId`, `ArtifactId`, `PublicationId`, `ShareId`, `UndoId`, `MaskId` and `ConfirmationId`. They carry no title, path, URI or timestamp meaning. Stored IDs are TEXT; shared RenderRequest.sourceId/pageId receive the wrapped `.value`, preserving its frozen signature.

Hashes are lowercase 64-character SHA-256 hex strings validated at boundaries. Hash inputs use tagged, length-delimited, versioned canonical encodings, checked Long dimensions and tightly packed RGB rows without stride padding. `RecipeCodec.encode/decode/hash` from the implementation plan includes all effective defaults, rejects unknown fields for execution and preserves unsupported serialized bytes as opaque history. Times are INTEGER Unix epoch milliseconds for audit/retention; they are not uniqueness or concurrency tokens. Runtime cancellation/deadlines use monotonic clocks, not wall time. Enums are stable explicit TEXT names rather than Kotlin ordinals. Durations, byte lengths and counters are Long; image dimensions/ordinals are Int with checked multiplication widened to Long.

### Result and settings vocabulary

`OperationError(code: OperationErrorCode, retryable: Boolean, safeMessageKey: String, affectedId: String?)` has no raw exception/URI in its serializable payload. Codes include INVALID_INPUT, UNSUPPORTED_FORMAT, UNSUPPORTED_VERSION, PERMISSION_LOST, SOURCE_UNAVAILABLE, SESSION_EXPIRED, REVISION_CONFLICT, PROVIDER_UNAVAILABLE, INVALID_MAP, PROCESSING_FAILED, RESOURCE_LIMIT, STORAGE_FAILED, CANCELED and INTEGRITY_FAILED. Map to RenderStatus only at the rendering boundary; PERMISSION_LOST is not silently flattened into PROCESSING_FAILED in the UI.

- `IngestResult.Committed(sessionId, documentId, pageId, sourceId, sourceByteHash, sourcePixelHash, documentRevision)` means durable accepted bytes, normalized identity and exactly one page commit. `IngestResult.Rejected(sessionId, error)` means no new visible page; `IngestResult.Pending(sessionId, recoveryState)` means an interrupted recoverable operation, not success. Cancellation uses the distinct error/state, not an empty successful list.
- `SaveRecipeResult.Saved(pageId, recipeRevision, documentRevision, recipeHash)` identifies the new immutable revision. `Conflict(actualRevision)` and `Rejected(error)` do not mutate current pointers. expectedRevision compares the current page recipe revision, not documentRevision.
- `ExportSettings(format: ExportFormat, pages: List<PageOutputSettings>, pdf: PdfSettings?, jpeg: JpegSettings?, acceptedDegraded: List<AcceptedExecution>)` contains only supported typed fields. `ExportFormat` is PDF/JPEG/PNG. `PageOutputSettings(pageId, output: OutputSpec, fallbackPolicy: FallbackPolicy=FAIL, requestedOutput: OutputSpec=output)` uses EXPORT purpose for both outputs. Normally requestedOutput equals output; output is the actual raster size approved for encoding. Its list must equal the reviewed active page order, with no missing/extra/duplicate IDs. `PdfSettings` stores physical-page rule, nominalDpi, margin rule, writerId/version and admissionProfileVersion; `JpegSettings` stores quality, encoderId/version and declared chroma policy `YUV444` or `PLATFORM_VERIFIED` with expected sampling factors. Only supported settings for the chosen format may be non-null. PNG has lossless rendered-RGB semantics, not a quality field.
- `AcceptedExecution(pageId, recipeRevision, executionHash, renderId: RenderId, actualSize: PixelSize, rasterPixelHash: String)` binds explicit degraded acceptance to a previously shown, durably committed lossless RenderedPage produced by an EXPORT-purpose request with KEEP_STAGE_INPUT. executionHash covers the canonical requested source/recipe/mask/provider identities, requestedOutput, fallback policy, executed StageRecords and omissions, DEGRADED status, actualSize and rasterPixelHash; transient timings are excluded. Preserve file-byte hash separately. A review lease pins the record/file before showing acceptance; freeze transfers retention to the snapshot. No wildcard acceptance, preview upscaling, rerun-and-accept-whatever or lossy checkpoint is permitted.
- `ExportSnapshot(snapshotId, documentId, documentRevision, snapshotHash, settings, pages: List<ExportPageSnapshot>, createdAt)` is immutable. Each page entry includes ordinal, PageId, SourceId/SourceBlobId, byte/pixel hashes, normalized PixelSize, conversionFingerprint, Recipe revision/canonical bytes/hash, mask identities/hashes, provider identities/assetSetHash, renderer version, requestedOutput, actual output, fallbackPolicy and optional acceptedRenderId/acceptedExecutionHash. It references no mutable current pointer. For an accepted entry fallbackPolicy must be KEEP_STAGE_INPUT and output.size must equal AcceptedExecution.actualSize; a differing size requires renewed review of dimensions, rotation/stage omissions, physical placement and resource admission before freeze. An ordinary entry requires FAIL and matching requested/actual outputs; a newly encountered degradation fails that export and requires a new reviewed snapshot.
- `ExportResult.Ready(snapshotId, artifactSet: List<ExportArtifact>)` means the complete verified private set. `ExportArtifact` includes ArtifactId, ordinal, MIME, byteCount, sha256, output dimensions/page-count metadata and verification status, not a public file path. `Failed(snapshotId, error)` and `Pending(snapshotId, state)` preserve completed checkpoints but cannot be reported as Ready.
- `RecoveryReport(inspected: Long, completed: Long, resumed: Long, quarantined: Long, blocked: Long, safeIssues: List<RecoveryIssue>)` counts actual reconciler actions. An issue exposes opaque operation ID, state/error and permitted user action, not private URIs. Zero issues is not evidence of hardware power-loss durability.

For the non-result canonical methods, validation failures use a typed `RepositoryFailure(OperationError)` and cancellation propagates CancellationException. UI adapters convert these to structured UI state; no raw Room/provider exception escapes to a user message. A revision conflict in freezeExport throws the typed conflict before creating a snapshot. No partial snapshot is returned.

### Supporting document/session methods

Use suspending repository commands `beginImport(documentId: DocumentId, expectedDocumentRevision: Long, anchorPageId: PageId?): ImportBatch`, `reserveImportItems(sessionId: ImportSessionId, count: Int): ImportBatch`, `bindImportItem(sessionId: ImportSessionId, ordinal: Int, uri: Uri): ImportSessionId`, `renameDocument(documentId: DocumentId, expectedDocumentRevision: Long, title: String): DocumentMutationResult`, `reorderPages(documentId: DocumentId, expectedDocumentRevision: Long, pageIds: List<PageId>): DocumentMutationResult`, `duplicatePage(pageId: PageId, expectedDocumentRevision: Long): DocumentMutationResult`, `rotatePage(pageId: PageId, expectedRecipeRevision: Long, clockwiseQuarterTurns: Int): DocumentMutationResult`, `removePage(pageId: PageId, expectedDocumentRevision: Long): DocumentMutationResult`, `undoDocumentEdit(undoId: UndoId, expectedDocumentRevision: Long): DocumentMutationResult` and `deleteDocument(documentId: DocumentId, expectedDocumentRevision: Long, confirmationId: ConfirmationId): DocumentMutationResult`. `DocumentMutationResult` is `Applied(documentRevision, affectedPageIds, undoId?)`, `Conflict(actualRevision)` or `Rejected(error)`. `ImportBatch` contains parent ID and ordered child IDs. beginImport persists the parent before launching a picker; reserveImportItems creates children only after the actual selection count is known and checked, or count=1 before camera capture. Observe library/editor metadata with Flow; no file decode occurs inside a Room transaction.

The parent ImportSessionId is a BATCH; its ITEM child IDs are what `SourceStore.ingest` consumes. Bind every returned URI to its reserved ordinal before enqueueing. The same child ID can only bind once; a changed URI requires explicit restart/new child ID. New user imports create new sessions even for the same URI; retries reuse a session. Enforce one active insertion batch per document or transactionally queue batches. Reserve stable placeholder PageIds/relative positions in session rows, not visible Page rows, so asynchronous completions preserve selected order. The parent's expectedMembershipToken is a canonical hash of the active PageId order; item commits CAS it and advance it for their own insertions, while ordinary recipe edits do not change it. Concurrent membership/reorder/deletion while an insertion batch is unresolved requires a visible finish/cancel choice or a CAS conflict. Do not silently pick a different insertion location when the anchor disappears.

Live U-04/FR-17 adds a distinct album recipe-edit batch, not an ImportSession: data-owned `BatchRecipeChange(pageId:PageId, expectedRecipeRevision:Long, recipe:Recipe)` and suspend `DocumentRepository.applyBatchRecipes(documentId:DocumentId, expectedDocumentRevision:Long, changes:List<BatchRecipeChange>):DocumentMutationResult`. [BATCH_EDITING](BATCH_EDITING.md) fixes nonempty/unique same-document inputs, final independent per-page recipes, full revision/membership/source validation, one all-or-nothing metadata transaction, one documentRevision increment and one BATCH_RECIPE_EDIT UndoEntry. Reuse existing Applied/Conflict/Rejected; aggregate Conflict reports actual document revision and successful Applied returns all changed PageIds/non-null undoId. No repeated saveRecipe loop or import-batch identity may masquerade as atomic recipe saving. No source/pixel/EXIF mutation, render-inside-transaction, silent partial save or changed frozen export. Required tests supplement T-03/T-09/T-10; no application schema or implementation exists yet.

`ConfirmationId` is a short-lived private token bound to the displayed document ID, page count, documentRevision and action. The repository verifies it and the revision inside the transaction; a generic affirmative button from another document cannot authorize deletion. Source GC after a confirmed logical purge is constrained cleanup, not deletion authority for external documents.

## Proposed Room schema version 1

The following is the complete initial relational shape; actual Room annotations/DDL must be reviewed and schema-exported at implementation. `?` means nullable; all other columns are NOT NULL. `PK(a,b)` means a composite primary key. Every FK has an index beginning with its referencing columns. FKs use RESTRICT/NO ACTION unless an explicit join-row CASCADE is stated; a user document delete must not cascade into source files or frozen page copies. Blob fields hold bounded canonical metadata/masks, never original image bytes. Validate invariants both in repository commands and SQL constraints/triggers where Room's supported schema permits them.

## Private directory layout and identity

## File transaction and recovery state machine

DESIGN state machine for ingest and derived private files: `INTENT → COPYING → SEALED → MOVED → COMMITTED`. Distinct exits are `CANCELED`, `RETRYABLE`, `QUARANTINED` and `FAILED`. A visible page/Ready artifact exists only after COMMITTED metadata. All transitions are conditional on transaction ID and current state, and replay is idempotent. A Room journal row is created before filesystem side effects; journal state can lag the filesystem, which is why reconciliation inspects both.

1. **INTENT:** transactionally allocate stable IDs and record the intended owner, final/staging relative paths, canonical parameters and session. The item session reserves its planned PageId and insertion slot. No Page or Source READY row is exposed.

   Camera capture reserves this intent before shutter IO and writes only its separate capture.part handoff. Ingestion reads that closed handoff into original.part; a crash/cancel before camera completion remains an uncommitted session, not a valid source. Only the recorded item/transaction may use this private-URI exception.
2. **COPYING:** create only this transaction's staging directory/file, exclusively. Stream once, hash/count, enforce format/input limits, validate normalized pixel identity under admitted decode and collect bounded provenance. On cancellation or failed read no visible page is committed. A full staging payload without a seal is not assumed valid.
3. **SEALED:** finish validation, flush and sync the payload using supported file-descriptor primitives, close it, write/sync a canonical seal and journal its hash/expected length. Stage and final roots are on the same app-private filesystem. Atomic same-filesystem rename/move is used only where the platform/filesystem actually supplies it; verify the implementation and sync directory entries where available. Best-effort sync is not a claim of survival against every hardware/power failure.
4. **MOVED:** move the complete sealed payload to its exclusive final path, never replace a source. Inspect a preexisting final file against this operation's expected hash/length before reuse; mismatch means INTEGRITY_FAILED/quarantine. Persist the observed move state. A crash before that database update can leave SEALED plus a valid final file; reconciliation must discover it.
5. **COMMITTED:** in one Room transaction recheck live session/document/anchor/capacity and stable operation identity; insert/reuse verified SourceBlob/Source, Page/RecipeRevision, SourceReference rows and counters, finish the item session and increment documentRevision. Record FileTransaction.COMMITTED in the same transaction. Import identity uniqueness prevents a second page on replay. A canceled/deleted destination cannot be resurrected by recovery.
6. Finalization can release temporary URI grants and prune this transaction's staging/seal according to the application's authorized retention policy. Cleanup failure does not reverse a valid page commit and must not lead to deleting its final source. Never ask a source provider to delete the user's original as part of import cleanup.

Byte dedup is optional. If enabled, first compare byte hash/length, then verify byte equality on a potential collision before sharing a SourceBlob; only link a READY winner and add its reference transactionally. The hash/length lookup is deliberately indexed but not unique, so concurrent imports can safely retain two equivalent immutable blobs instead of racing to replace a file. Future compaction must use the same ownership/reclaim protocol. Pixel-hash equality is a render/cache identity check, not permission to discard a byte-distinct original. On crypto-hash collision/mismatch, preserve/quarantine separate evidence and fail safely rather than overwriting either user's source.

### Crash-boundary decisions

| Observed Room/filesystem boundary | Required idempotent reconcile behavior |
|---|---|
| No intent, unexpected staging/final entry | Never attach it to a document by filename. Quarantine under bounded recovery reporting; do not auto-delete a potentially unique original. |
| INTENT with no file | Resume only if source grant/session is still valid, otherwise require reselection; no page created. |
| COPYING with partial/no seal | Revalidate/restart into a new attempt, preserving retry identity; do not trust a partially written hash. A provider URI may be unavailable. |
| Valid seal and staging file, journal behind | Verify seal/payload identities and destination session, then advance to SEALED and complete move/commit. |
| SEALED but only final file exists | Verify expected final length/hash and seal, infer MOVED, then complete exactly one metadata commit. |
| Both staging and final exist | Verify both and expected identity; use the recorded final only if valid. Retain conflicting data in quarantine; never choose by newest timestamp. |
| MOVED, metadata not committed | Recheck session/owner; commit once if still intended, otherwise retain as unreferenced recovery data pending safe policy. Do not insert into a different document. |
| Metadata COMMITTED, journal replay | Return existing committed IngestResult/artifact; no new source reference/page/revision. Validate required file presence on recovery/open. |
| Metadata points to missing/corrupt source | Mark source/document affected state read-only with INTEGRITY_FAILED and recovery UI. Search only owned recorded staging/quarantine matches; never fabricate content, rewrite recipe binding or claim recovery succeeded without matching bytes. |
| File valid, metadata unknown/future version | Preserve file and opaque rows; do not destructively reset the database or reinterpret old journals. |
| Disk full/sync/rename/Room commit failure | Keep the last durable state, return STORAGE_FAILED/Pending, retain recoverable payload and retry idempotently. No half-published page/export. |

## Reference lifetimes and safe reclamation

Owners of a source include live/removed pages, retained recipe history, Undo entries, import handoff, immutable export pages, pending/running jobs and source-aligned masks. Each owner creates one SourceReference per required SourceId; removal uses the identical owner key and is idempotent. An export page independently pins its source even if its original Page row is purged. An active share pins its artifact, and an artifact pins its snapshot until retention ends. Never decrement pins merely because the UI navigated away or WorkManager emitted a transient state.

Garbage collection is a journaled, narrowly scoped operation. In a Room transaction, verify all ownership rows, count equality, no unresolved file transaction/lease/snapshot and any required permanent-delete confirmation; mark the exact source DELETING with a reclaim TransactionId. New references to DELETING sources are rejected or wait for reconciliation. Recheck the file identity/path before moving it into the operation's private quarantine/reclaim location. Only after removal of the exact confirmed unreferenced payload is acknowledged may final metadata be purged. Restart completes the same reclamation or restores the verified file; it never deletes a newly referenced replacement by path coincidence.

Do not delete SourceBlob bytes until every normalized Source record is unreferenced and removed, no snapshot/job/history/mask still needs them, and SourceBlob.sourceCount agrees with actual rows. Different conversion versions may retain separate normalized identities for one blob; user quarter-turns never create such records. Purging a document first consumes its named confirmation and changes lifecycle; cancel or preserve its jobs explicitly. Existing frozen exports may continue by deliberate retention policy, and their document tombstone stays until references end. External provider originals and externally published/recipient-made copies are never GC targets. Cache eviction may delete only regenerable unleased previews, not durable originals, committed checkpoints still pinned, or shared files with active retention.

DESIGN privacy retention: session URI strings/grants end at completed copy or abandonment; transient failed staging is surfaced for retry/cleanup rather than retained invisibly forever. Completed private exports are user-visible and retained until explicit deletion or a disclosed retention rule; share copies have their separate 24-hour policy. Actual in-app deletion does not promise cryptographic or flash-level erasure. A cleanup action must respect the application's user permissions and the specification-authoring task confers no authority to delete workstation files.

## Schema evolution and integrity verification

VERIFIED DOCUMENTATION: Room supports explicit/manual and supported automatic migrations, schema export and migration testing; fallback-to-destructive-migration can permanently delete database data. The currently inspected guide contains newer Room-family examples, so its code is not a dependency pin. [Migration guide, inspected through Svipall 2026-11-14](https://developer.android.com/training/data-storage/room/migrating-db-versions). DESIGN: pin a stable compatible Room family at bootstrap and use that family's actual APIs; never mix room/room3 snippets or guess version compatibility.

Export every released schema under `data/schemas/` in the future app. No destructive fallback in production, including downgrade and unknown-version cases. Test every supported upgrade path from populated real-version fixtures, not only empty databases, and compare fresh schema to migrated schema including FK/index constraints. Preserve canonical old recipes/execution records; schema migration does not recompute source hashes using a new conversion policy or rewrite original bytes.

File-layout changes have their own versioned journal and migrate one verified object at a time, with enough free-space preflight and crash recovery; a Room migration cannot make them atomic. Keep old decoder/recipe versions available for retained documents where feasible, or preserve read-only unsupported access/exported artifacts explicitly. Unsupported future databases open through a safe failure/recovery route without reset; rollback/backup strategy must itself obey no-cloud/privacy policy and avoid a partial DB-only copy missing WAL/files. Never copy a live SQLite main file alone and call it a coherent backup.

Validate DB foreign keys/reference consistency, source length/hash on first recovery/open as policy requires, and every export input before rendering. A missing file becomes a visible integrity failure with preserved metadata and recoverable source candidates, not silent page disappearance. Thumbnail cache repair cannot repair missing originals. Keep integrity tools local and bounded; do not transmit pixels/URIs for diagnosis.

## Required tests and evidence — future work

- `recoverAllIngestJournalBoundaries`: interrupt before/after intent, part creation/write, validation, payload sync, seal write/sync, rename, MOVED update, row commit and cleanup; reconcile twice and prove exactly one page or a truthful uncommitted failure.
- Concurrent repeated result/worker starts: unique child session and job key prevent duplicate page/reference/artifact; lease fencing prevents a late runner from publishing.
- SourceByte/SourcePixel identity: padding excluded, EXIF 1–8/ICC/alpha conversion version included, user quarter-turns change only recipe/render identity, byte-distinct originals not lost through pixel dedup.
- CAS/history: recipe conflict, document-order conflict, Undo creates new revisions, duplicate pages edit independently, canceled import cannot attach after document switch/deletion.
- Reference tests: duplicate/remove/Undo/history/snapshot/job/mask/share retention prevent premature GC; stale stored counters cannot authorize deletion; a source cannot gain a reference after DELETING without recovery.
- Freeze/isolation: mutate current recipe/order/delete page after freeze and verify exact original snapshot render order/settings/source/asset hashes remain; unknown version/missing asset blocks execution without mutation.
- Actual filesystem/Room integration: low storage, short writes, rename and DB failures, orphan conflicts, WAL/migration population and process death; fake-filesystem tests alone are insufficient.
- Publication/share: provider output close before Room commit, unreadable readback, revoked permissions, partial external file, exact-target cleanup, grant expiry and recipient-copy boundary.

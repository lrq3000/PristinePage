## Capture session and UI ownership

`app/.../capture/CameraController.kt` owns CameraX use cases; `CaptureSession.kt` owns stable `ImportSessionId`, intended `DocumentId`, insertion anchor and operation state. Compose observes lifecycle-aware state rather than retaining camera or native-image ownership. A session is stored before launching an external activity or starting a shutter operation; its result is not routed to whichever document happens to be visible later.

1. Enter capture without requesting permission on app startup. Ask for CAMERA only after Take photo. Refusal, permanent refusal, permission auto-reset and runtime revocation leave Import photos and Library usable. Explain a Settings route without repeatedly reopening permission dialogs.
2. Bind Preview and ImageCapture together to the capture destination's lifecycle, using a CameraProvider/use-case group when the shared viewport is needed. Stop orientation listeners and release destination-owned bindings when leaving. CameraX lifecycle binding manages camera opening/session closure with lifecycle transitions; it does not authorize an application-wide camera session. [CameraX architecture, inspected 2026-11-14](https://developer.android.com/media/camera/camerax/architecture).
3. Default to the back camera and a manual shutter. No live detector or optional model is required. Expose supported flash Off/Auto/On, disable unsupported modes, and distinguish torch from still flash. Handle unavailable/busy/disconnected cameras as actionable failures, not black-screen success.
4. Update ImageCapture target rotation from the display/orientation policy, including locked-orientation screens; snapshot the effective rotation at shutter time. Avoid changing camera use cases merely because Compose recomposes. Serialize shutter admission and use a new operation ID for every intentional capture.
5. Capture JPEG into the operation's app-private `capture.part` handoff, never a gallery path, with a reserved item session/journal intent before camera IO. Success means a closed, validated file accepted through the same `SourceStore` ingestion protocol as imports, not merely receipt of a camera callback. SourceStore copies the closed handoff into the transaction's distinct `original.part` payload and validates it; never open the same file for simultaneous source read and destination truncation. A private file URI may be used internally for that protocol; it never leaves the process or enters a share Intent. Restrict this internal URI path to the staging root and recorded transaction ID, and retain the handoff until commit or explicit abandonment.
6. Capture-in-flight navigation/backgrounding may cancel before ingestion or complete privately into the originally bound session. A callback validates session state and target document existence; a canceled session or deleted document cannot receive a late page. Retain an uncommitted recoverable result only under a visible recovery state, not as an unrelated library page.

A `CaptureSession` has `CREATED → WAITING_PERMISSION → CAMERA_READY → CAPTURING → INGESTING → COMMITTED`, with distinct `DENIED`, `CANCELED`, `PERMISSION_LOST`, `FAILED` and `INTERRUPTED` outcomes. Persist durable operation identity, not a live CameraX object or bitmap in saved-state bundles. Reopening must reconcile before offering Resume. Rotation/recreation restores the same session; explicit New document creates another one.

### Preview, capture and source orientation are different spaces

**Manual debug preview slice:** The shutter reserves a bound album BATCH before opening CameraX. The non-exported, non-grantable, UID-checked staging bridge exposes only that batch's private cache JPEG to the existing ingest controller after CameraX returns success. It neither meets full durable per-item-before-shutter recovery nor promises an automatic reshoot after recreation; an interrupted shot is canceled or explicitly abandonable. Full flash/locked-orientation behavior and CAP-01–03 device acceptance remain open.

VERIFIED DOCUMENTATION: PreviewView applies preview transformations; CameraX outputs comprise buffers plus transformation information. For file ImageCapture, the crop rectangle is applied before saving and orientation is represented by EXIF. CameraX configuration also warns that HAL behavior may alter buffer and/or metadata. Therefore decode the returned file's actual metadata, not an assumed sensor angle. [Transform output, page updated 2026-11-12, inspected 2026-11-14](https://developer.android.com/media/camera/camerax/transform-output); [configuration options, inspected 2026-11-14](https://developer.android.com/media/camera/camerax/configuration).

DESIGN: persist the captured JPEG bytes unchanged and apply EXIF exactly once in the normalized decode. Record actual encoded size, crop, effective rotation, lens direction and conversion version as provenance. Do not rotate the bitmap once for CameraX and a second time for EXIF. Front-camera preview mirroring is not permission to mirror the saved source; v1 need not expose a front-camera selector, but any exposed camera must pass asymmetric orientation tests.

Use an explicit transform chain `analysis buffer → crop → rotation → viewport → PreviewView` for an optional overlay. A shared viewport aligns the field of view but does not make analysis, preview and saved-still pixel dimensions equal. On accepting a still, rerun corner detection on the actual orientation-normalized still and validate manual controls there. An earlier overlay is only a suggestion. If reusing a proposal experimentally, map through recorded transforms and validate against the still; never just multiply by a preview/still width ratio. Different dimensions, crops or rotation invalidate the transfer and require still detection/manual reset. All geometric formulas remain in [GEOMETRY_ALGORITHMS.md](GEOMETRY_ALGORITHMS.md).

1. Before launch persist session/document/anchor identity; use Activity Result registration stable across recreation. Cancel returns no page and does not create a blank document success. After process death, a missing or mismatched session produces an explicit expired-result action, not attachment to a new editor.
2. Enforce the document's remaining page capacity after the picker result, including fallback over-selection. Ask the user to reduce an oversized selection; do not silently import only its first items. Show per-item failure and retained successful pages for a mixed valid/corrupt batch.

4. Stream to a transaction-owned private `.part`, computing SHA-256 and counting actual bytes. A provider-reported length is advisory and can be null or false. Enforce the byte cap during the read, close streams on cancellation, and treat zero-byte/short/error results as uncommitted failures. Never reopen a provider stream for rendering after a private copy has committed.
5. Validate the staged bytes, compute normalized identity under admitted decode, sync/seal/move and atomically commit metadata/page ownership through the journal protocol. Release any persisted grant after committed copy or final abandonment; a retry retains it only while its private session explicitly needs it. Catch revocation at open, during read and on release.
6. A copied source remains readable if the provider later revokes access, moves/deletes its document or disappears. A copy that did not finish is not a saved page. Persistable grants themselves can become unusable after provider movement/deletion. Cloud-backed picker entries are not an offline guarantee. Read only bytes currently available through the provider; show bounded pending/cancel behavior for stalled providers, close the descriptor on cancellation where supported, and do not promise a timeout can interrupt every provider implementation. The production app never initiates a cloud login/download itself. Refuse unavailable content with Retry/reselect guidance and keep camera/library/local imports usable.

### Input and decode policy

The following are **DESIGN starting limits**, shared with PERFORMANCE_AND_OFFLINE, not measured supported maxima: encoded bytes ≤100 MiB, source metadata ≤48,000,000 pixels, each long edge ≤12000, and ≤100 active pages per document. Use checked Long arithmetic for all sizes/strides/products, validate after orientation as well as before allocation, and compare actual decoded dimensions against header claims. These ceilings do not authorize allocations and do not imply 100 full-resolution pages fit a PDF writer.

| Input property | Required handling |
|---|---|
| Format | Accept actual JPEG, static PNG and static WebP signatures supported by the pinned decoder. MIME and extension are hints only. Reject PDFs, SVG, video, animated/multiframe images, virtual/coerced documents, unsupported codecs, truncated payloads and conflicting structure. Do not silently select an animation's first frame. |
| Tiny/extreme image | Reject zero dimensions. Geometry requiring a two-dimensional domain rejects width or height below 2. A readable tiny photo may be retained with a low-detail warning and no upscaling, but cannot enter an incompatible geometry mode. Highly elongated images can pass metadata limits only if decoder/geometry/export admission also passes; no unchecked aspect division or giant intermediate padding. |
| Decode bomb | Inspect actual container dimensions/frame structure before decode; enforce bounded metadata parsing, byte cap and real allocation admission. Revalidate decoder output. Never use repeated full-decode retries to discover whether an enormous image fits. Untrusted ICC/EXIF chunk lengths are bounded by encoded bytes and parser checks. |
| Memory | Use the shared tracked allocation budget `min(192 MiB, max(32 MiB, 0.5 × memoryClassMiB))`, accounting for concurrent Java/native buffers, decoder copies and UI retention. Metadata acceptance alone is not full-decode permission. Use a verified bounded row/region decode if available, otherwise reject an over-budget full decode without producing a lower-resolution source identity. |
| Corruption | Require complete supported decode, finite valid dimensions and canonical pixel hash before page commit. Do not accept a partial-image decoder's repaired result as the unchanged original's valid rendering. Retain recoverable staging only under explicit failure state. |
| Metadata | Preserve metadata only in immutable original bytes and private bounded provenance. GPS, device serials, maker notes, comments and user filenames are not propagated into rendered exports, PDF metadata, thumbnails, logs or share names. |

### Canonical orientation, color and pixel identity

DESIGN: decode into a validated opaque encoded-sRGB RGB8 image, matching `RgbImage`. Read raw pixels without automatic orientation if the bridge applies its own transform; if the selected decoder automatically orients, record and test that behavior and do not apply EXIF again. The conversion version pins decoder bridge, color transform, alpha-composition convention and orientation policy. Different decoder/platform results that change pixels require a different conversion fingerprint, not reuse of an old pixel hash.

For encoded dimensions W,H, map original pixel centers `(x,y)` to normalized coordinates as follows. Missing EXIF means orientation 1; invalid/out-of-range metadata is rejected rather than guessed. All eight cases require asymmetric fixtures and actual decoder tests.

| EXIF | Normalized `(x',y')` | Output size |
|---|---|---|
| 1 | `(x,y)` | W,H |
| 2 | `(W−1−x,y)` | W,H |
| 3 | `(W−1−x,H−1−y)` | W,H |
| 4 | `(x,H−1−y)` | W,H |
| 5 | `(y,x)` | H,W |
| 6 | `(H−1−y,x)` | H,W |
| 7 | `(H−1−y,W−1−x)` | H,W |
| 8 | `(y,W−1−x)` | H,W |

Unprofiled ordinary SDR inputs are interpreted as sRGB. Supported embedded SDR RGB profiles are explicitly converted to sRGB before quantization; record the profile SHA-256, transform implementation and version. API 26 support must be demonstrated through the chosen bridge, not inferred from a newer ImageDecoder API. Reject malformed/unsupported profiles, CMYK/YCCK JPEGs without a validated conversion, high-bit-depth inputs without a validated SDR path, HDR/HLG/PQ or gain-map images and unknown transfer functions. V1 does not silently ignore a gain map, tone-map HDR or treat Display-P3 bytes as sRGB. A separately approved conversion mode would need its own contract and consent.

After color conversion to encoded sRGB, composite alpha onto white using straight-alpha samples and the pinned byte rule `out=roundByte(alpha*color+(1−alpha)*255)`. If the bridge supplies premultiplied samples, explicitly unpremultiply/convert with tested rounding or use a bridge that yields straight samples; alpha zero becomes white without division. Do not assume Android's canvas compositing produces this exact byte convention. PNG export preserves these final opaque rendered bytes, not the source's original transparency.

`sourceByteHash` is SHA-256 of every unchanged encoded byte. `sourcePixelHash` is SHA-256 of a domain-tagged, length-delimited canonical stream containing conversion fingerprint, normalized width/height and tightly packed RGB rows, excluding row padding. Compute the full-source identity, not a preview hash. User page rotation is not source normalization: it changes only `GeometryRecipe.outputQuarterTurns` and recipe/render identity, never this source pixel hash/binding, source bytes or EXIF state. Decode/color acceptance is a release gate; support not demonstrated by the pinned bridge remains rejected and visible.

## Multi-page document editing

Use stable document/page/source IDs, never list indices in jobs or navigation. A document overview supports add from camera/photos, accessible move earlier/later and drag reorder, duplicate, clockwise/counterclockwise quarter-turn, remove with Undo, rename, reopen and explicitly confirmed permanent document deletion. Reorder and page membership changes increment documentRevision; recipe Apply increments recipeRevision and documentRevision in one Room transaction. Rotate changes only `GeometryRecipe.outputQuarterTurns:Int` in 0..3, with a new recipeRevision/documentRevision. There is no second Page.rotation/source-rotation field. Source-space corner/curve controls and masks remain unchanged; display-transform their handles for interaction and inverse-transform edits back into the original oriented-source space.

Output rotation follows the base geometry and precedes appearance. Odd turns swap the base target width/height before choosing final OutputSpec dimensions. The renderer composes the shared inverse quarter-turn map, including q1 `(u,v)→(v,1−u)`, with base geometry and applies it identically to image/protection/coverage once; it does not resample an intermediate bitmap again or reapply EXIF. Exact NONE/full-frame source-sized turns use exact pixel permutations. GEOMETRY_ALGORITHMS owns the complete maps and GEO-07 oracle; capture/storage must not invent a parallel rotation algorithm.

Duplicate creates a new PageId, independent current-recipe pointer and history, but shares the immutable source through reference accounting. Remove first creates a tombstone and Undo record; the source cannot be reclaimed during that retention or while a snapshot/job pins it. DESIGN initial Undo retention is the most recent 20 document edits for 24 hours, explicitly displayed; this is metadata retention, not a claim of secure deletion. Permanent document deletion requires a named confirmation and cannot remove external copies. Pending exports read their pinned snapshot pages even if the editable document subsequently changes or is removed.

## Export review and snapshot

`DocumentRepository.freezeExport(documentId, expectedDocumentRevision, settings): ExportSnapshot` is suspending. Perform one consistent Room read/write transaction that validates the reviewed revision and pins the complete ordered page list, source byte/pixel identities, immutable Recipe revisions/canonical bytes/hashes, conversion fingerprints, protection masks, exact ProviderIdentity/asset hashes/runtime/precision, render version and requested/actual OutputSpec for every page. PageOutputSettings and ExportPage explicitly store fallbackPolicy, default FAIL; accepted fallbacks additionally freeze acceptedRenderId and acceptedExecutionHash under DATA_MODEL_AND_STORAGE. No worker rereads `Page.currentRecipeRevision` or current page order after freezing.

Show unsaved-draft choices before freeze: Apply or exclude/discard the draft. Pending source commits, unknown schema versions, invalid serialized input/masks, missing required files and unsupported combinations block freeze with per-page reasons. Ordinary pages also require valid geometry and locally available hash-matched provider assets; changed/missing assets fail explicitly rather than substituting another provider. An explicitly accepted degraded entry is the documented exception to solution/provider re-execution checks: it pins an already verified lossless EXPORT-purpose fallback raster and its execution record instead of re-running the failed solution or provider. Structural/source/schema/rights/resource checks remain mandatory, and invalid-input/canceled/resource/storage failures cannot be accepted as fallbacks. Pending/read-only snapshot pages cannot be edited in place. The editor can continue through new document revisions; the export review labels newer edits as excluded.

`ExportSettings` chooses PDF, JPEG or PNG; exact page dimensions; physical-page rule/DPI; encoder settings; and explicit degraded-execution acceptance if applicable. Normal export first resolves the base target and swaps targetW/targetH for odd outputQuarterTurns, then selects `s=min(1,4000/max(targetW,targetH),sqrt(12_000_000/(targetW*targetH)))`, floors scaled dimensions and validates geometry's minimum 2×2 requirement. Never upscale solely to manufacture detail; reject an extreme aspect whose floored dimension is below the required minimum rather than distorting it. The UI displays chosen pixel dimensions before confirmation. Full-source target is a separate optional choice subject to admission. CARD 224 and PREVIEW 1024 long-edge limits are not export dimensions.

`ExportService.export(snapshotId: ExportSnapshotId): ExportResult` returns a verified app-private artifact set, not an external-write or recipient-delivery promise. Each committed page render uses the DATA_MODEL_AND_STORAGE pre-execution key including pageId, recipeRevision/hash, sourcePixelHash, outputSpec, mask hashes, conversion/render/encoding versions, assetSetHash, effective backend/precision and fallbackPolicy. FAIL and KEEP_STAGE_INPUT requests are distinct jobs; same-policy retries reuse only their respective job. The resulting execution hash joins this key only for the completed-raster cache, not pre-execution idempotence. Retry reuses only a fully verified matching file/execution record; identical key with different canonical input is a corruption error. Canceled/resource/storage failures publish nothing new. The journal precedes WorkManager enqueue; scheduler deferral/force-stop does not become a completion promise. [WorkManager scheduling guidance, inspected 2026-11-14](https://developer.android.com/develop/background-work/background-tasks/persistent).

Degraded acceptance is not a checkbox permitting arbitrary future failures. First commit the exact complete fallback as a lossless RenderedPage with actual dimensions, pixel/file hashes, canonical EXPORT request, KEEP_STAGE_INPUT policy, DEGRADED execution and omitted stages/rotation; a review lease protects it from cache eviction. A preview-sized result cannot be upscaled into this record. Review its actual raster and effective orientation. If retained source/crop dimensions differ from the requested output, renew size/physical-page/resource review and set PageOutputSettings.output to those actual dimensions while preserving requestedOutput. Freeze pins that exact render/reference and hashes both outputs, policy and acceptance. The worker verifies and encodes this raster without geometry, appearance, added rotation, resizing or re-inference. Lost/changed data fails, rather than silently generating a new fallback. A new degradation on an ordinary frozen page requires a new review/snapshot; none can be accepted automatically midway through export.

### JPEG and PNG

DESIGN: render once from each frozen page, then encode its requested image format to a private staged file. Use opaque sRGB, orientation 1, no GPS/comments/private source metadata and a sanitized neutral output name with page ordinal. JPEG is lossy; initial quality 92/100 is a proposed default, not a fidelity measurement. Pin the encoder and controlled chroma policy: use 4:4:4 for text/color-edge fidelity when the selected encoder exposes and validates it; a platform encoder with unconfigurable subsampling cannot be labeled 4:4:4. If that bridge is retained, freeze `PLATFORM_VERIFIED` with its measured/inspected sampling policy and make PNG the lossless alternative. Verify actual JPEG SOF sampling factors against the declared policy for each output; a backend policy change fails/reopens acceptance rather than silently changing chroma behavior. Unsupported sampling controls are disabled with an explanation. No proprietary preset or named compatibility mapping is required.

Carnet named JPEG and Image ZIP offer exactly three JPEG quality presets: Maximum (100), Balanced (92, default), and Smaller file (80). This choice leaves Image size and the rendered raster unchanged, is not presented for PDF, and remains lossy even at Maximum. Freeze the same effective `android_bitmap` v2 settings for every JPEG member of the reviewed artifact. The writer may omit only the redundant single ICC wrapper inserted by the platform encoder on its freshly created sRGB bitmap; source profile admission and original bytes are never changed. Verify actual 4:2:0 sampling, closed file decode and raster comparison before readiness. Legacy settings stay readable, with existing artifacts unchanged. See the [CARNET-JPEG-02 evidence](../../validation/export/carnet-jpeg-platform-profile.md) for limits.

PNG is lossless relative to the final rendered RGB raster and uses no JPEG-quality setting. It does not make the enhancement/geometry lossless relative to the photograph. Read back encoded dimensions, actual format, full decode and hash; PNG decoded RGB must equal rendered RGB, while JPEG uses separately approved content/color tolerances, not byte equality. Store SHA-256 and byte length of the actual encoded artifact and its execution record. Multi-page image export is an ordered set of independent files, not a mislabeled single JPEG/PNG. Offer share-multiple or repeated Save as; directory-tree batch publication is optional and needs its own explicit destination consent, not broad storage access.

### Image-only multi-page PDF: selected v1 policy

VERIFIED DOCUMENTATION: Android `PdfDocument` accepts pages sequentially and writes the document after page completion; it is not thread-safe. One active page does not imply one retained page in memory. Inspected AOSP `PdfDocument.cpp` stores `PageRecord` objects in `mPages`, retains completed `SkPicture` recordings in `finishPage()`, iterates them in `write()` and releases them in `close()`. This verifies a retention concern in that inspected source, not a universal byte-per-pixel bound for every Android build. [Android API reference, inspected 2026-11-14](https://developer.android.com/reference/android/graphics/pdf/PdfDocument); [AOSP source, blob d21eb3f6a208e7f339f056b1163fc26ba07860c3, inspected 2026-11-14](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/libs/hwui/jni/pdf/PdfDocument.cpp).

An established permissive alternative is [PdfBox-Android](https://github.com/TomRoush/PdfBox-Android), whose inspected README describes an Android PDFBox port, API 19+ functionality and Apache-2.0 licensing of its main code. That establishes a reuse candidate, not a verified low-memory Android writing path, current maintenance/security acceptance or a license audit of every optional dependency. No artifact was installed or benchmarked. A disk-backed/streaming library could reduce native retention only after its exact Android write path, resource behavior and dependency notices are verified.

DESIGN DECISION: v1 uses platform `PdfDocument` for **admitted multi-page image-only PDFs**, avoiding an additional full PDF library before there is a measured need. It renders/commits pages individually to private files, then assembles one PDF on a single owner thread. Do not claim page checkpointing makes final platform assembly streaming or bounded independently of total page pixels. No custom PDF writer is specified: the verified native retention gap justifies a future established-writer evaluation if measured limits prove insufficient, not premature PDF syntax/security maintenance.

Whole-document preflight is mandatory. The PDF admission estimator includes retained page recordings/images for **all** pages, peak current-page decode/draw buffers, PDF encoding/write workspace, retained UI assets and verification raster memory. The general processing budget in PERFORMANCE_AND_OFFLINE is an upper bound, not reserved exclusively for PDF. A provisional estimate may conservatively charge at least `8*sum(pagePixels)` bytes for retained image/copy exposure plus explicitly counted working buffers and writer overhead; **8 is an initial planning coefficient, not a verified upper bound**. Admission additionally requires a measured writer profile for the supported OS/backend and dimension/page-count envelope, with a justified safety margin. Account for Java/native ownership; measure PSS separately. If the profile is missing or the full request exceeds it, refuse that request with RESOURCE_LIMIT before allocation. Never hope an OutOfMemoryError will recover a killed process.

The release gate must retain a validated envelope supporting at least a two-page, mixed-aspect PDF at explicitly shown usable dimensions on the minimum supported device class, plus successful normal-size examples on the nominated target devices. Multi-page export is mandatory and cannot ship as an unimplemented placeholder or a universal refusal. No evidence exists yet for a numeric safe maximum. The proposed 100-page library limit is not a PDF guarantee. When a request is too large, offer an explicitly reviewed smaller pixel size, a user-chosen subset or per-page images; never silently resize, truncate, split or mark a partial document complete. Larger validated envelopes may be added by measured profile version, not an unsupported blanket promise.

DESIGN physical sizing: choose either image-aspect pages or a named paper size with aspect-preserving contain and white margins, never stretch/crop by default. PDF units are points, 72 points/inch; for an image-aspect page requested at finite positive nominal D DPI use `widthPt=72*pixelWidth/D`, `heightPt=72*pixelHeight/D`. D=300 is an initial physical-size default, not an inferred optical capture resolution. Platform PageInfo uses integer sizes, so round physical dimensions once as `floor(value+0.5)` with no byte clamp and reject nonpositive/Int-overflow results; record actual MediaBox. Preserve raster aspect with contain within that rectangle and record the actual placed contentWidthPt/contentHeightPt; effective `dpiX=72*pixelWidth/contentWidthPt`, `dpiY=72*pixelHeight/contentHeightPt` uses the placement, not page margins. For tiny images whose chosen nominal DPI rounds a page axis to zero, require an explicit different physical-page choice rather than constructing an invalid PDF page. A paper choice such as A4 uses `mm*72/25.4`, independently of source pixels. Physical page size and image-pixel detail are different settings; changing metadata DPI does not add detail. PageInfo's integer arguments and PostScript-point units are documented in the [official PageInfo.Builder reference, updated 2026-08-03, inspected 2026-11-14](https://developer.android.com/reference/android/graphics/pdf/PdfDocument.PageInfo.Builder).

Draw each completed opaque raster into the declared content rectangle; no OCR text layer, hidden attachment, source filename/GPS, password/encryption or PDF/A guarantee. Platform PDF compression is backend-controlled; do not advertise the per-page JPEG quality slider as a guaranteed PdfDocument compression/subsampling knob. Freeze PDF writer/profile version and supported settings separately. Always finish a started page, write/flush/close the private document and close the PdfDocument in finally scopes. Do not recycle a bitmap that the native recording may still reference; its lifetime/retention must be included in admission until verified safe.

Private PDF validation checks nonzero complete file, SHA-256, byte length, independent page count, per-page MediaBox/aspect and raster readability using an independent renderer/parser. Distinctive mixed-aspect fixture marks establish order and placement. Structural success alone does not prove pixel fidelity; decode/raster comparisons have documented tolerances. In-app Android PdfRenderer may provide production readability checks, with additional independent test tooling in the acceptance suite; parser choice and its measured verification memory are bootstrap/implementation decisions, not claims of testing already performed.

## Private completion, SAF Save as and sharing

First finish and verify an app-private artifact set; journal its hashes and mark PRIVATE_READY in Room. Only then launch destination selection/share. The private completion state survives destination cancellation, revocation or failure and remains available for retry. An `ExportResult.Ready` is not a claim that a provider or another app retained the data.

VERIFIED DOCUMENTATION: ACTION_CREATE_DOCUMENT is a Save as operation and does not overwrite an existing same-name file; the system chooses a distinct name. SAF providers expose capabilities, not a universal atomic rename/replace transaction. Persistable access does not survive every provider move/deletion. [SAF guide, inspected 2026-11-14](https://developer.android.com/training/data-storage/shared/documents-files). DESIGN inference: do not advertise all-or-nothing external publication based on app-private rename semantics.

1. Persist a publication attempt bound to ExportSnapshotId, artifact hash, expected MIME/length, consent and operation ID before launching ACTION_CREATE_DOCUMENT. Store returned URI privately. Recheck that it is the result of this exact pending destination request after recreation.
2. Copy the complete private artifact to the newly created URI, with bounded buffers, byte-count/hash verification of the bytes sent, flush and successful close. Where granted/readable, reopen and independently hash/count the external bytes. `OUTPUT_COMPLETED` means provider write/close acknowledgment; `READBACK_VERIFIED` additionally means the reopened bytes matched. Neither promises cloud synchronization or external durability beyond the provider contract. Do not label readback verified if unsupported.
3. On short write, close failure, provider error, cancellation or permission loss mark the canonical `PARTIAL_EXTERNAL`, `FAILED`, `CANCELED` or `PERMISSION_LOST` state as applicable, keep PRIVATE_READY, and display the exact status. Never report success merely because a destination URI exists. A process death after provider close but before local commit creates `NEEDS_VERIFICATION`, not automatic success or blind rewrite; reconcile by readback where possible, otherwise ask for a new Save as attempt.
4. Cleanup is best effort only for the exact newly created target owned by this recorded attempt, and only if deletion is supported and ownership/consent remain certain. If cleanup is unavailable, show that an incomplete external file may remain and identify it within the private UI. Do not delete another document, recursively clean a tree, or reuse an old URI to overwrite without a separate explicit confirmation. Providers may expose bytes before close and rename/delete may be non-atomic.
5. For a multi-file JPEG/PNG set, retain per-artifact publication outcomes. A successful subset is not completion of the entire requested set. Retry missing artifacts through new destination selections unless an explicitly authorized resumable provider operation is proven safe.

Sharing consumes only verified PRIVATE_READY exports. Copy/link them into the narrowly exposed private `filesDir/shared-exports/<shareId>/` area under a recorded retention lease; never expose source, DB, journal or arbitrary cache roots. Use FileProvider content URIs, exact MIME, ACTION_SEND or ACTION_SEND_MULTIPLE, EXTRA_STREAM/ClipData and FLAG_GRANT_READ_URI_PERMISSION, without write or prefix grants. FileProvider must be non-exported with grantUriPermissions enabled. Intent grants are temporary and tied to recipient activity-stack/service lifetime; explicit package grants require explicit revocation or reboot. [FileProvider reference, inspected 2026-11-14](https://developer.android.com/reference/androidx/core/content/FileProvider).

The chooser is not a delivery receipt; do not show “recipient saved” from its callback. DESIGN retention: keep a share-ready copy for 24 hours and while a known local lease is active, offer Stop sharing, and revoke grants during expiry/cleanup before removing app-owned share files. File opens and display-name/size queries require the same active durable lease, even if an Android grant or private copy still exists. A query without a live lease returns no rows. Lifecycle/Doze may delay cleanup; the UI must not promise exact-time grant revocation. Previously disclosed names, already opened descriptors and recipient-made copies cannot be recalled. No broad external-storage permission is added for sharing. Detailed threat boundaries and backup exclusions are in SECURITY_PRIVACY.

# Atelier acquisition — private staging and publication

Companion to [Atelier](ATELIER.md) and [Capture, import and export](CAPTURE_IMPORT_EXPORT.md). This is a proposed storage boundary and validation sequence, not a shipped or migrated database.

## Avoid rebinding a committed ingest

The existing Room ingest requires an active document and records its exact ID in the session, journal, inserted page and commit receipt. Committed replay explicitly compares the current page's document ID to that intent. Moving the same page into another document after staging breaks replay. Likewise, inserting directly into a saved target and compensating on Cancel would expose partial pages and revisions, and could race unrelated edits. Avoid both approaches.

## Recommended reuse boundary

Keep an internal *staging document* per acquisition draft and bind every camera/picker operation to it. Add an explicit durable draft row in the same Room database, not a title prefix or preference flag. A single transaction creates the staging document plus the row, so no crash between those writes can leak an empty album into Home. The staging document remains `ACTIVE` for trusted draft-bound editing/ingest, but both catalog queries exclude staging identities (including retained terminal staging rows). Public album lookup by an opaque ID must also distinguish draft-only from saved scope; the retained wizard uses a draft-aware lookup. Old application data does not become staging as a result of migration.

The draft row contains `draftId`, `stagingDocumentId`, optional `targetDocumentId`, optional expected target revision, state (`ACQUIRING`, `EDITING`, `COMMITTED`, `ABANDONED`), generation, current step, selected page ID in staging, and committed document ID where applicable. No picker URI or pixel data enters the record. Expose the minimum trusted operations: open/resume, reserve one camera/gallery/file batch, authenticated operation completion, freeze for editing, step/page checkpoint, resume acquisition, confirm accumulated recipe changes, publish, and abandon. Use the Room revision and ordered active staging pages as membership witnesses. `Finish importing` is blocked until every bound ingest child has reached a settled state or is explicitly canceled and fenced. It freezes the ordered successful staging page IDs and prevents a delayed callback from adding pages after that step. Reopen a pending draft from its opaque ID and committed source owners; do not consume an Android URI solely because it was seen before process death.

## Atomic final publication

For a new album, publishing may expose the same staging document as an ordinary saved album, by atomically transitioning the draft row and removing its *hidden* status, without changing ingest identity. Set the saved timestamp and keep an idempotent publication receipt. For an append, leave staging journal/source/page relationships intact. Instead create new `PageId`s in the target using each verified retained `SourceId` and a newly bound initial recipe from the accepted staging recipe. Preserve exact staging order, source normalization/hash, and already-saved target pages. Reuse the existing single-source/multiple-page reference ownership pattern. Update target membership/revision and the publication receipt once, atomically. A stale target revision or capacity violation publishes none; a retry after a successful but unacknowledged commit returns the exact receipt rather than producing duplicates. Do not publish absent, invalid, cross-source, or render-unchecked geometry as successful.

Already-appended or abandoned staging data is not available under ordinary Home or page/album entry points. Before implementing abandonment or reclamation, reconcile historical source/page references, terminal journals and interrupted copy owners via the existing retention service. Do not unlink originals, clear unrelated provider grants, or delete a shared asset by scanning a directory. Establish a bound for unpublished and retired staging retention before admitting repeated abandoned large drafts.

## Implementation and gates

The independent storage review identified three gates before enabling live staging: saved-by-ID album and page reads must exclude active drafts too; freeze/abandon and ingest completion must share a transactional generation fence; append must reject a pending target import even when the target revision is unchanged. Bind the ordered append ID mapping and exact render-checked staging recipe revisions to its receipt. Canceled jobs do not prove obsolete source ownership ended. Enforce a cumulative staging-byte and draft-count cap, including interrupted inputs, before accepting repeated work.

The internal host checkpoint reserves the current 100 MiB maximum encoded payload for each new `INGEST` attempt owned by a hidden staging document, including canceled, unsealed and superseded attempts. Eight slots bound encoded payloads to 800 MiB per charged draft, with at most two charged drafts. An abandoned draft with no copy intents does not consume a slot. A successfully published album ceases charging its committed copies, now ordinary saved originals, but its failed or interrupted copies remain charged. This bounds encoded copy payloads, not all metadata, and does not reclaim files. Any later retention implementation must retain the charge until the owned bytes and journal are reconciled; deleting metadata first would incorrectly free capacity.

The internal recipe checkpoint renders the exact requested draft recipe through the trusted coordinator with `PREVIEW` sizing and `FAIL` fallback. Reject a mismatched request, degraded/failed result, incorrect dimensions, or closed raster before mutation; do not persist the bitmap. After rendering outside the Room transaction, recheck editing generation, page/source membership, the expected recipe revision, and its immutable bytes before writing private history. A recipe identical to the current one is rendered and rechecked without advancing its revision. This per-page checkpoint does not attest to a final ordered album save, native decoder performance, or full-target export.

The internal album publication command takes the exact ordered page IDs and reviewed revisions/hashes, not a mutable selection. It performs another trusted render per ordered page before the final transaction; the transaction rechecks the frozen draft, source and exact page/history pins, immutable recipe rows, and target revision/pending imports. It then creates one new album or appends without rebinding staging IDs, recording a bounded receipt in the same transaction. A completed receipt can acknowledge only the matching generation and full ordered request. The current local candidate exposes this route for validation; native migration/recovery and usable terminal retention remain integration gates.

The local review screen precedes Finish importing. Wizard page/step changes checkpoint that editor's current verified draft before navigation. Confirming Skip perspective resets only the geometry of newly staged pages, taking existing rotation and appearance from each guarded private recipe. Each changed recipe checkpoints individually, so an interruption may leave some resets private; retry is idempotent and the wizard advances only after the complete reset. No saved album or original is modified by the skip itself.
